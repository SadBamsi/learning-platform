> **Ответ за 30 секунд.** Сначала различите **виды состояния**: локальное UI-состояние компонента (`useState`), общее клиентское (тема, корзина, модальные окна), **серверное** (данные с API — это кэш, а не «ваше» состояние), состояние URL (фильтры, страница) и состояние форм. Для каждого свой инструмент. **Context** — механизм **передачи** значения вниз без «пробрасывания пропсов», а не стор: при изменении `value` перерисовываются **все** потребители, и выбрать часть значения нельзя. Он хорош для редко меняющихся данных (тема, пользователь, локаль). Для частых обновлений и большого общего состояния используют внешний стор: **Redux Toolkit** (строгая модель, DevTools, middleware) или **Zustand/Jotai** (минимум кода, подписка на срез через selector). Серверные данные — **TanStack Query / SWR** (кэш, дедупликация, повторные запросы, инвалидация), а не `useEffect` + `useState`. Первое правило: держите состояние как можно ближе к месту использования.

## Виды состояния

| Вид | Примеры | Инструмент |
|---|---|---|
| Локальное UI | открыт ли dropdown, значение поля | `useState`, `useReducer` |
| Общее клиентское | тема, корзина, фильтры интерфейса | Context, Zustand, Redux Toolkit |
| Серверное | список заказов, профиль | TanStack Query, SWR, RSC/loader'ы фреймворка |
| URL | страница, сортировка, поиск | роутер (`searchParams`) |
| Формы | значения, ошибки, touched | `react-hook-form` и аналоги, Actions |

Типичная ошибка новичка — складывать **всё** в один глобальный стор. Серверные данные и URL лучше не копировать в стор: у них свой источник правды.

## Context

```jsx
const ThemeContext = createContext("light");

function App() {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext.Provider value={theme}>
      <Page />
    </ThemeContext.Provider>
  );
}

function Button() {
  const theme = useContext(ThemeContext);     // в React 19 можно и use(ThemeContext)
  return <button className={theme}>OK</button>;
}
```

Контекст решает **prop drilling** (протаскивание пропсов через промежуточные компоненты). Если Provider отсутствует, `useContext` вернёт значение по умолчанию из `createContext(default)` (проверено: `default-value`). Часто делают обёртку-хук, которая выбрасывает ошибку при отсутствии провайдера.

### Почему Context — не «стор»

1. **Все потребители перерисовываются** при любом изменении `value` (сравнение через `Object.is`). Выбрать часть значения (как selector) нельзя.
2. Если `value` — объект, созданный в рендере (`value={{ user, n }}`), он **новый на каждый рендер провайдера**, и потребители перерисовываются, даже если данные те же. Проверено: потребитель в `memo` перерисовывается при `value={{ a: 1 }}` и **пропускает** рендер при `value` из `useMemo`.
3. Если контекст содержит `{ a, b }`, а компонент использует только `a`, он всё равно перерисуется при изменении `b` (проверено). Разделение на два контекста устраняет рендер (проверено).

Как уменьшать лишние рендеры:

- **Мемоизировать `value`** (`useMemo`), особенно если провайдер часто перерисовывается из-за родителя.
- **Разделять контексты** по частоте изменений и по ролям: например, отдельно значение и отдельно `dispatch` (функция `dispatch` из `useReducer` стабильна).
- **Передавать потомков как `children`**: проверено, что при изменении состояния провайдера перерисовывается только компонент, читающий контекст, а остальные дети (созданные выше) пропускаются.
- Для сложных сценариев — внешний стор с подпиской на срез.

**Паттерн «Context + useReducer»:**

```jsx
const StateCtx = createContext(null);
const DispatchCtx = createContext(null);

function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });
  return (
    <DispatchCtx.Provider value={dispatch}>
      <StateCtx.Provider value={state}>{children}</StateCtx.Provider>
    </DispatchCtx.Provider>
  );
}
```

Компоненты, которым нужен только `dispatch` (кнопки «добавить»), не перерисовываются при изменении корзины.

## Внешние хранилища

**Redux Toolkit** — «официальный» способ Redux: единый стор, `createSlice` (редьюсеры с Immer — можно писать «мутирующий» код, получая иммутабельное обновление), `createAsyncThunk`, RTK Query для запросов, мощные DevTools и middleware. Уместен в больших приложениях с командой, где нужны единые соглашения и трассировка действий.

**Zustand** — минималистичный стор без провайдера:

```jsx
const useBearStore = create((set) => ({
  bears: 0,
  increase: () => set((s) => ({ bears: s.bears + 1 })),
}));

const bears = useBearStore((s) => s.bears);          // подписка на срез
const increase = useBearStore((s) => s.increase);
```

Компонент перерисовывается, только если выбранное значение изменилось. Для выбора нескольких полей одним объектом используют `useShallow` (иначе новый объект на каждый вызов селектора считается «изменением»).

**Jotai** — атомарная модель: маленькие независимые атомы, зависимости между ними вычисляются.

**Как выбирать:** есть 3–5 общих значений, редко меняются → Context; много общего клиентского состояния и частые обновления → Zustand/Jotai; большая команда, сложные потоки действий, нужен аудит → Redux Toolkit; данные с сервера → TanStack Query/SWR.

### useSyncExternalStore

Хук React для подписки на **внешний** источник данных (стор, `window.matchMedia`, `navigator.onLine`). Он гарантирует согласованность при конкурентном рендеринге (нет «разрыва» — tearing). Минимальный стор:

```jsx
function createStore(initial) {
  let state = initial;
  const listeners = new Set();
  return {
    getState: () => state,
    setState: (patch) => {
      state = { ...state, ...(typeof patch === "function" ? patch(state) : patch) };
      listeners.forEach((l) => l());
    },
    subscribe: (l) => { listeners.add(l); return () => listeners.delete(l); },
  };
}

const store = createStore({ count: 0, name: "ann" });
const useStore = (selector) =>
  useSyncExternalStore(store.subscribe, () => selector(store.getState()));
```

Проверено: компонент, выбравший `count`, перерисовывается только при изменении `count`, а выбравший `name` — только при изменении `name`.

Важное требование: `getSnapshot` должен возвращать **одно и то же значение, если данные не менялись**. Селектор, создающий новый объект (`s => ({ c: s.count })`), нарушает это правило: проверено — React выбрасывает «Maximum update depth exceeded». Поэтому в Zustand для выбора нескольких полей используют `useShallow`.

## Серверное состояние

Данные с сервера — **кэш чужого состояния**: они могут устареть, их нужно перезапрашивать, дедуплицировать, инвалидировать после изменений. Делать это руками (`useEffect` + `useState`) — значит заново писать кэш с гонками, загрузкой и ошибками.

```jsx
// чтение
const { data, isPending, error } = useQuery({
  queryKey: ["todos"],
  queryFn: getTodos,
});

// запись + инвалидация
const qc = useQueryClient();
const add = useMutation({
  mutationFn: addTodo,
  onSuccess: () => qc.invalidateQueries({ queryKey: ["todos"] }),
});
```

Проверено запуском (TanStack Query v5): два компонента с одним `queryKey` выполнили **один** запрос, после мутации и `invalidateQueries` данные обновились в обоих (всего два запроса).

Что даёт библиотека: кэш по ключу, дедупликацию запросов, повторные запросы при фокусе окна и ошибке, состояния `isPending`/`error`, оптимистичные обновления, пагинацию и бесконечные списки, инвалидацию. Значения по умолчанию (по документации): `staleTime: 0` (данные считаются устаревшими сразу), `gcTime` — 5 минут для неиспользуемых запросов.

В Next.js часть серверных данных получают на сервере (серверные компоненты) — тогда клиентскому коду нужен меньший кэш; но интерактивные клиентские данные (поиск, бесконечная прокрутка, мутации) по-прежнему удобно вести через TanStack Query.

## Частые follow-up вопросы

**Что такое prop drilling и как с ним бороться?**
Передача пропсов через несколько уровней, которым они не нужны. Решения: композиция (`children`, передача готовых элементов), Context, внешний стор.

**Когда Redux всё ещё нужен?**
Большие приложения, где важны единые соглашения, трассировка действий, middleware и инструменты отладки; также если он уже есть в проекте.

**Context заменяет Redux?**
Нет: Context — транспорт значения, у него нет селекторов, middleware и отладки; для частых обновлений он неэффективен.

**Как избежать лишних рендеров в Context?**
Мемоизировать `value`, разделять контексты, использовать `children`, при необходимости перейти на стор с селекторами.

**Чем `useSyncExternalStore` лучше `useEffect` + `useState` для подписки?**
Он согласован с конкурентным рендерингом (нет tearing), корректно работает при SSR (`getServerSnapshot`) и проще.

**Нужно ли хранить данные с сервера в Redux?**
Обычно нет: RTK Query/TanStack Query даёт специализированный кэш.

## Типичные ошибки

- Один глобальный контекст/стор на всё приложение.
- Часто меняющиеся данные в Context.
- `value={{...}}` в Provider без `useMemo`.
- Копирование серверных данных в локальный стор.
- Селектор, создающий новый объект на каждый вызов (без `useShallow`/мемоизации).
- Хранение производных данных в сторе вместо вычисления.
- Дублирование состояния URL в `useState`.
