> **Ответ за 30 секунд.** По умолчанию перерисовка родителя перерисовывает всех детей. **`React.memo(Component)`** пропускает рендер компонента, если его `props` **поверхностно** равны прежним (`Object.is` для каждого пропса). Но объекты, массивы и функции, созданные в теле родителя, каждый раз новые, поэтому `memo` без **стабильных ссылок** не срабатывает. **`useCallback(fn, deps)`** сохраняет функцию между рендерами, **`useMemo(() => value, deps)`** — результат вычисления; это одно и то же с точки зрения механизма (`useCallback(fn, d)` ≈ `useMemo(() => fn, d)`). Использовать их стоит, когда есть измеримая проблема: дорогое вычисление, тяжёлое дерево под `memo`, стабильная зависимость для эффекта или другого хука. Мемоизация «везде» усложняет код и сама стоит ресурсов. Начиная с **React Compiler** (стабильная версия 1.0) такие оптимизации можно переложить на сборку: компилятор автоматически запоминает значения и JSX, если код следует правилам React.

## Что именно спрашивают

- «Почему `memo` не помогает, если передавать в проп `() => {}` или `{}`?»
- «Что такое поверхностное сравнение? Можно ли передать свой компаратор?»
- «Как ускорить тяжёлый список/форму, не добавляя `memo` везде?»
- «Нужна ли мемоизация при использовании React Compiler?»

## React.memo и поверхностное сравнение

```jsx
const Row = memo(function Row({ item, onSelect }) { /* ... */ });
```

`memo` сравнивает каждый проп из старого и нового наборов через `Object.is`. Если все равны — рендер пропускается. Проверено на компоненте `Child`, обёрнутом в `memo`, при клике по кнопке родителя:

| Что передаём | Рендер `Child` |
|---|---|
| только примитивы (`label="x"`) | пропущен |
| инлайн-функция `onClick={() => {}}` | **выполняется** |
| инлайн-объект `cfg={{ a: 1 }}` | **выполняется** |
| `useCallback`-функция | пропущен |
| `useMemo`-объект | пропущен |
| JSX-элемент в пропе (`label={<b>x</b>}`) | **выполняется** (новый элемент каждый раз) |

То же с `children`: если родитель создаёт `<Box><span>static</span></Box>` внутри своего рендера, `children` — новый объект при каждом рендере, `memo(Box)` не помогает (проверено).

`memo` не блокирует рендер, вызванный **изменением собственного состояния** компонента или **контекста**, который он читает (проверено: свой `useState` в `memo`-компоненте рендерит его).

**Свой компаратор** (`memo(Comp, (prev, next) => boolean)` — вернуть `true`, если рендер можно пропустить):

```jsx
const Row = memo(Row, (a, b) => a.user.id === b.user.id);
```

Опасность: если сравнить не все влияющие поля, интерфейс **устареет**. Проверено: компаратор сравнивал только `id`, и после смены `name` на экране осталось старое имя. Глубокое сравнение в компараторе тоже стоит ресурсов, поэтому его применяют редко.

## useCallback и useMemo

```jsx
const handleSelect = useCallback((id) => setSelected(id), []);          // функция
const visible = useMemo(() => items.filter(byQuery(q)), [items, q]);    // значение
```

Оба хука запоминают результат и пересчитывают его, только если изменились зависимости (сравнение `Object.is`). **Сами по себе они ничего не ускоряют**: смысл появляется, когда стабильная ссылка или кэш кому-то нужны.

Проверка (список из 5 строк, ввод текста в поле родителя, рендеры `Row`):

| Вариант | Рендеров `Row` при вводе |
|---|---|
| без мемоизации | 5 |
| только `memo(Row)` | 5 (колбэк каждый раз новый) |
| только `useCallback` | 5 (`Row` не обёрнут в `memo`) |
| `memo(Row)` + `useCallback` | **0** |

Вывод: `memo` и `useCallback` работают **в паре**. Мемоизированный колбэк без `memo` у потребителя бесполезен, и наоборот.

### Когда это действительно нужно

1. **Дорогое вычисление при рендере** (фильтрация/сортировка тысяч элементов, тяжёлый расчёт). Сначала измерьте (`console.time`, React Profiler): в документации ориентир — вычисление заметно дольше ~1 мс. Проверено: `useMemo` пересчитывает значение только при изменении `query`; два несвязанных обновления дали 0 пересчётов.
2. **Стабильные пропсы для `memo`-потомков** (большой список, сложная форма).
3. **Стабильная зависимость для эффекта или другого хука** (объект/функция в `useEffect([...])`, чтобы эффект не перезапускался).
4. Значение — зависимость другого `useMemo`/`useCallback`.

### Когда не нужно

- Дешёвые вычисления (`a + b`, короткий `.map`). Мемоизация стоит памяти и сравнения зависимостей и ухудшает читаемость.
- Если у потребителя нет `memo` и значение не идёт в зависимости.
- Если зависимости меняются на каждом рендере (кэш ни разу не сработает).

**Гарантий нет:** `useMemo` — оптимизация, а не семантика. React может сбросить кэш (например, в разработке или по своим причинам). Код должен оставаться корректным и без кэша.

Частая ошибка: **побочные эффекты в `useMemo`** (запросы, подписки) — для этого есть `useEffect`. И неполные зависимости: `useMemo(() => f(a, b), [a])` вернёт устаревший результат при смене `b`.

## Сначала структура, потом memo

Часто лишние рендеры устраняются без `memo`:

1. **Опустить состояние вниз.** Если состояние нужно только маленькой части интерфейса, вынесите эту часть в отдельный компонент. Проверено: тяжёлый компонент рядом с полем, у которого есть своё состояние, рендерится 1 раз при вводе; если состояние вынесено в обёртку с `children`, — 0.
2. **Передавать тяжёлое как `children`** (см. тему про рендеринг): элемент создан выше, и React пропускает его.
3. **Виртуализация длинных списков** (`react-window`, `@tanstack/react-virtual`): вместо оптимизации 10 000 строк рендерим только видимые.
4. **Дробить контекст** и не складывать в один контекст часто меняющиеся и редкие данные (см. тему про state management).

## React Compiler

React Compiler — плагин сборки (Babel и интеграции для Vite, Next.js и других), который **автоматически расставляет мемоизацию**: запоминает значения, функции и JSX между рендерами, если входы не изменились. Проверено на `babel-plugin-react-compiler 1.0.0`: родитель без `useCallback`/`useMemo` передаёт в `memo`-компонент функцию и объект, созданные в теле; **без компилятора** `Child` рендерится при клике по кнопке родителя, **с компилятором** — 0 раз.

Что важно знать:

- Компилятор опирается на **Rules of React**: чистые компоненты, отсутствие мутаций `props`/`state`, хуки по правилам. Код, который их нарушает, он пропускает или компилирует неверно. Для отдельного компонента есть выход `"use no memo"`.
- Он не отменяет ответственности за архитектуру: избыточное состояние, огромные списки и тяжёлые вычисления остаются вашей заботой.
- Существующие `useMemo`/`useCallback` можно оставить: полезно, когда нужно явно управлять зависимостями эффекта.
- В новых проектах и при включённом компиляторе `React.memo` обычно не требуется (так сказано в документации React).

## Частые follow-up вопросы

**Чем `useMemo` отличается от `useCallback`?**
Первый запоминает результат вызова функции, второй — саму функцию. `useCallback(fn, deps)` — сокращение для `useMemo(() => fn, deps)`.

**Почему `memo` не сработал?**
Среди пропсов есть нестабильная ссылка (инлайн-функция, объект, JSX, `children`), либо компонент рендерится из-за собственного состояния/контекста.

**Сравнивает ли `memo` глубоко?**
Нет, поверхностно: ключ за ключом через `Object.is`.

**Нужно ли оборачивать всё в `memo`?**
Нет: каждая проверка пропсов стоит ресурсов, а польза только там, где рендер дорог и пропсы стабильны. Сначала измерьте (Profiler).

**Можно ли передать в `memo` свой `areEqual`?**
Да, но вы отвечаете за полноту сравнения: ошибка даёт устаревший интерфейс.

**Что делает `memo` с контекстом?**
Ничего: при изменении контекста компонент перерисуется независимо от `memo`.

## Типичные ошибки

- `memo` без стабилизации объектов/функций в пропсах.
- `useCallback`/`useMemo` без потребителя, которому нужна стабильная ссылка.
- Неполные зависимости (устаревшие значения).
- Побочные эффекты внутри `useMemo`.
- Мемоизация дешёвых вычислений «на всякий случай».
- Компаратор `memo`, сравнивающий не все поля.
- Оптимизация без замеров (Profiler, `console.time`).
