> **Ответ за 30 секунд.** Concurrent-рендеринг (React 18+) — возможность React **прерывать, откладывать и возобновлять** рендер, чтобы срочные обновления (ввод, клик) не ждали тяжёлых. Это **не многопоточность**: поток всё тот же, меняется планирование. Основные инструменты: **`useTransition`** — пометить обновление состояния как **несрочное** (`startTransition(() => setTab("b"))`), получить флаг `isPending`; **`useDeferredValue(value)`** — получить «отстающую» копию значения, которая обновляется после срочных обновлений; **`Suspense`** — декларативно показать `fallback`, пока часть дерева «ждёт» данные или код (`lazy`, `use(promise)`). Вместе с переходом Suspense **не заменяет уже показанный интерфейс fallback'ом**: остаётся старое содержимое, а `isPending` сообщает о загрузке. Условие: рендер должен быть чистым (иначе прерывание и повтор дают побочные эффекты), а один компонент, который сам рендерится долго, прервать нельзя — прерывание возможно между компонентами.

## Срочные и несрочные обновления

Без transitions любое `setState` — срочное: React отрисует его как можно скорее, и если рендер тяжёлый, интерфейс «замирает». С concurrent-рендерингом обновления делятся на:

- **срочные** — реакция на прямое действие: ввод в поле, клик, нажатие клавиши;
- **переходы (transitions)** — смена экрана, фильтрация большого списка: результат может появиться чуть позже.

Если во время рендера перехода приходит срочное обновление, React **отбрасывает** недорисованный переход, обрабатывает срочное и затем возобновляет переход. Поэтому рендер обязан быть чистым: он может быть вызван, прерван и начат заново.

## useTransition

```jsx
function Tabs() {
  const [tab, setTab] = useState("posts");
  const [isPending, startTransition] = useTransition();

  function select(next) {
    startTransition(() => setTab(next));        // несрочное обновление
  }

  return (
    <>
      <button onClick={() => select("comments")}>Комментарии</button>
      <div style={{ opacity: isPending ? 0.6 : 1 }}>
        <TabContent tab={tab} />                 {/* тяжёлая вкладка */}
      </div>
    </>
  );
}
```

Проверено (тяжёлый компонент, имитация 30 мс):

```
App tab=a pending=true     ← срочный проход: интерфейс сразу показывает isPending
Slow render tab=a          ← старое содержимое
App tab=b pending=false    ← переход применён
Slow render tab=b
```

Особенности:

- Внутри `startTransition` помечается именно **обновление состояния**; `isPending` — `true`, пока переход не завершён.
- Нельзя помещать в переход **управляемое поле ввода** (его значение должно обновляться срочно). Разделяйте: значение поля — срочное состояние, результат фильтрации — переход или `useDeferredValue`.
- В React 19 в `startTransition` можно передавать и **асинхронную** функцию (так устроены Actions); `isPending` остаётся `true` до её завершения.
- Переход можно вызвать и без хука: `import { startTransition } from "react"` — но тогда нет `isPending`.

## useDeferredValue

Возвращает значение, которое **отстаёт** от исходного: сначала отдаёт старое, затем в фоне пересчитывает новое.

```jsx
function Search() {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);
  const stale = query !== deferredQuery;

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <div style={{ opacity: stale ? 0.6 : 1 }}>
        <HeavyList query={deferredQuery} />       {/* HeavyList обёрнут в memo */}
      </div>
    </>
  );
}
```

Проверено: при вводе сначала рендерится `App q="abc" dq=""` (срочный проход со старым `deferred`), затем `App q="abc" dq="abc"` и только после этого список. **Без `memo` у списка он рендерится дважды** (в срочном проходе со старым значением и в отложенном), с `memo` — один раз, потому что в первом проходе его пропсы не менялись. Поэтому `useDeferredValue` почти всегда идёт в паре с `memo` у потребителя (либо потребитель — дорогой компонент, чьи входы совпадают).

### useDeferredValue против debounce

| | debounce | `useDeferredValue` |
|---|---|---|
| Задержка | фиксированная (300 мс) | адаптивная: нет ожидания, если устройство успевает |
| Прерываемость | нет: после паузы тяжёлый рендер блокирует | да: срочный ввод прерывает фоновый рендер |
| Сетевые запросы | уменьшает число запросов | сам по себе запросы не сокращает (запрос по `deferredQuery` будет, но реже, чем по `query`) |

Для защиты бэкенда от лишних запросов нужен debounce; для плавного рендера тяжёлого интерфейса — `useDeferredValue`. Их можно сочетать.

### Transition или deferred value?

- Есть доступ к месту, где вызывается `setState` → `useTransition` (и `isPending`).
- Значение приходит снизу или из пропсов, а состоянием владеет не ваш код → `useDeferredValue`.

## Suspense

`<Suspense fallback={...}>` показывает запасной интерфейс, пока потомок «приостановлен» (ждёт код или данные).

```jsx
<Suspense fallback={<Skeleton />}>
  <Profile id={id} />
</Suspense>
```

Что умеет приостанавливать компонент:

- `lazy(() => import(...))` — код компонента;
- `use(promise)` — чтение промиса (и контекста);
- Suspense-совместимые источники данных: фреймворки (Next.js, Relay), TanStack Query в режиме suspense, серверные компоненты.

Границы можно **вкладывать**: ближайшая сверху Suspense показывает свой `fallback`; так экран появляется по частям.

### use(promise)

```jsx
function User({ id }) {
  const name = use(fetchUser(id));     // fetchUser возвращает КЭШИРОВАННЫЙ промис
  return <b>{name}</b>;
}
```

Проверено: с кэшем по `id` сначала виден `fallback`, затем `user-1`; при смене `id` без перехода снова показывается `fallback`.

**Нельзя создавать промис в рендере клиентского компонента:** каждый рендер создаёт новый промис, и React не может «запомнить» ожидание. Проверено: `use(new Promise(...))` внутри компонента оставляет `fallback` на экране бессрочно (более 0,8 с при промисе в 20 мс). Промис должен приходить из кэша/библиотеки/родителя (в Next.js — из серверного компонента как проп).

Отличия от `await`/эффектов: `use` можно вызывать условно (в отличие от хуков), он заставляет компонент приостанавливаться, а ошибка отклонённого промиса уходит в ближайший error boundary (см. тему про границы ошибок).

### Suspense + transition: без повторного fallback

Если при смене параметра обычное обновление приостанавливает уже показанный Suspense, пользователь снова увидит `fallback` (старое содержимое скрывается). В переходе React **оставляет старый экран** и ждёт новых данных.

Проверено на примере переключения пользователя (`id: 1 → 2`, загрузка 60 мс):

```
без перехода:  показывается fallback, потом user-2
в переходе:    остаётся user-1, isPending = true, затем user-2
```

Поэтому навигация и смена вкладок оборачиваются в `startTransition` (Next.js и роутеры делают это сами).

React может немного **задерживать показ загруженного контента** после `fallback`, чтобы избежать «мигания» при быстрых загрузках; точное значение — деталь реализации (в нашем наблюдении контент появлялся после полусекундной паузы, но не после 100 мс).

### Streaming SSR и selective hydration

На сервере Suspense позволяет сразу отправить HTML «оболочки» страницы, а медленные части дослать потоком позже. Клиентская **выборочная гидратация** оживляет уже пришедшие части и приоритизирует те, с которыми взаимодействует пользователь. Подробно — в разделе про Next.js.

## Ограничения и подводные камни

- **Прерывание происходит между компонентами**, а не внутри одной функции компонента. Если один компонент рендерится 200 мс, интерфейс всё равно заблокируется на это время (решение: разбить, виртуализировать, вычислить тяжёлое в воркере).
- Concurrent-фичи не ускоряют работу, а **улучшают отзывчивость** за счёт приоритетов; общий объём работы тот же.
- Побочные эффекты в рендере (мутации, запросы, `ref.current` в теле) перестают быть безопасными — их нужно убрать.
- `useDeferredValue` без `memo` у потребителя почти бесполезен (проверено).
- Внешнее состояние нужно читать через `useSyncExternalStore`, иначе возможны «разрывы» (tearing) при прерываемом рендере.

## Частые follow-up вопросы

**Concurrent-рендеринг — это многопоточность?**
Нет. JavaScript остаётся однопоточным; React дробит работу и расставляет приоритеты, уступая управление браузеру между порциями.

**Нужно ли включать «concurrent mode»?**
В React 18+ достаточно `createRoot`; возможности включаются по мере использования `useTransition`, `useDeferredValue`, Suspense.

**Что показывает `isPending`?**
Что переход ещё не завершён. Удобно для индикаторов (приглушить список, показать спиннер).

**Как не мигать скелетоном при переключении?**
Делать смену параметров в `startTransition`: остаётся старый интерфейс, `isPending` сообщает о загрузке.

**Можно ли ловить ошибки Suspense?**
Ошибка загрузки (отклонённый промис, ошибка `lazy`) уходит в ближайший error boundary.

**В чём разница `useTransition` и `startTransition`?**
Хук даёт `isPending` и привязан к компоненту; отдельная функция — без флага, её можно вызывать где угодно.

## Типичные ошибки

- Класть в transition управляемое значение поля ввода.
- `useDeferredValue` без `memo` у тяжёлого потребителя.
- Создавать промис в рендере и передавать в `use`.
- Ожидать, что transition ускорит один тяжёлый компонент.
- Забывать про `isPending` и не показывать пользователю, что идёт загрузка.
- Использовать debounce вместо `useDeferredValue` (или наоборот) без понимания разницы.
- Побочные эффекты в рендере при включённых concurrent-фичах.
