## Решения

### Задание 1

Логи после клика (при первом показе выведутся все компоненты):

```
Counter
Plain      ← тот, что внутри Counter
```

- `Counter` — сменилось его состояние.
- `Plain` внутри `Counter` — новый элемент создаётся при каждом рендере `Counter`, а `Plain` не обёрнут в `memo`.
- `Memo` пропускается: у него нет пропсов, `memo` сравнивает их поверхностно и видит, что ничего не изменилось.
- `Plain` из `children` пропускается: элемент `<Plain />` создан в `App`, а `App` не перерисовывался; `Counter` получает **тот же объект элемента**, и React не заходит внутрь.
- `App` не логирует, потому что его состояние не менялось и его родитель не перерисовывался.

### Задание 2

- а) **2** — тот же тип на той же позиции: состояние сохраняется.
- б) **0** — на позиции раньше был `Counter`, теперь `div` (другой тип), поддерево пересоздаётся.
- в) **2**. Слот под условный элемент существует всегда (`false` занимает позицию), поэтому `Counter` остаётся на той же позиции и сохраняет состояние при любом значении `flag`. Проверено запуском.
- г) **0** — разные `key` означают разные элементы.

### Задание 3

Причина: `key={i}` привязывает состояние `draft` к **позиции**, а не к сущности. После удаления первой строки строка `B` оказывается на позиции 0 и подхватывает состояние бывшей строки `A`. Проверено запуском: при `key=index` получаем `B=typed-in-A`, при `key=id` — `B=`.

Исправление — ключ из данных:

```jsx
{items.map((item) => (
  <Row key={item.id} item={item} onRemove={(id) => setItems(items.filter((x) => x.id !== id))} />
))}
```

Если у данных нет id, его нужно сгенерировать **один раз при создании элемента** (например, `crypto.randomUUID()` при добавлении в массив), а не в `render`.

### Задание 4

`Field` объявлен внутри `SearchForm`, поэтому на каждый рендер создаётся **новая функция** — для React это новый тип компонента. При вводе символа состояние меняется → `SearchForm` рендерится → `Field` теперь другой тип → старый `input` удаляется, создаётся новый. Фокус теряется. Проверено в jsdom: DOM-узел меняется после каждого символа, `document.activeElement` перестаёт указывать на `input`.

Способ 1 — вынести компонент на верхний уровень и передать данные пропсами:

```jsx
function Field({ value, onChange }) {
  return <input value={value} onChange={(e) => onChange(e.target.value)} placeholder="Поиск" />;
}

function SearchForm() {
  const [query, setQuery] = useState("");
  return <form><Field value={query} onChange={setQuery} /></form>;
}
```

Способ 2 — не создавать компонент, а вызвать JSX напрямую (инлайн или через переменную):

```jsx
function SearchForm() {
  const [query, setQuery] = useState("");
  const field = <input value={query} onChange={(e) => setQuery(e.target.value)} placeholder="Поиск" />;
  return <form>{field}</form>;
}
```

Вызывать функцию как `{renderField()}` тоже работает (хуков внутри быть не должно), но способ 1 предпочтительнее: проще тестировать и переиспользовать.

### Задание 5

```jsx
function ProfileForm({ userId }) {
  const [name, setName] = useState("");
  return <input value={name} onChange={(e) => setName(e.target.value)} />;
}

// в месте использования:
<ProfileForm key={userId} userId={userId} />
```

Смена `key` пересоздаёт компонент, а значит, состояние инициализируется заново. Проверено: после смены ключа поле пустое. Преимущество перед `useEffect`: нет промежуточного рендера, в котором в поле ещё показывается старое имя, и не нужно помнить о сбросе других состояний.

### Задание 6

Монтирование:

```
render Parent
render Child
layout Child
layout Parent
effect Child
effect Parent
```

Клик (обновление):

```
render Parent
render Child
layout cleanup Child
layout cleanup Parent
layout Child
layout Parent
effect cleanup Child
effect cleanup Parent
effect Child
effect Parent
```

Порядок проверен запуском. Render идёт сверху вниз; эффекты — снизу вверх (дочерние раньше родительских). Cleanup предыдущего эффекта выполняется **перед** запуском нового, и сначала для layout-эффектов.

### Задание 7

Пример ответа:

«Virtual DOM — это дерево React-элементов: объектов, описывающих, каким должен быть интерфейс. При обновлении состояния React вызывает компоненты и получает новое дерево. Затем reconciliation сравнивает его с предыдущим по эвристикам: разные типы — пересоздать поддерево, одинаковые — обновить, элементы списков сопоставляются по `key`. После этого в фазе commit React применяет к реальному DOM только найденные изменения, а потом запускает эффекты. Сам по себе Virtual DOM не делает React быстрее ручных операций с DOM: его ценность в декларативном стиле и предсказуемости. Производительность зависит от того, сколько компонентов перерисовывается, и поэтому важно держать состояние рядом с местом использования и мемоизировать там, где это измеримо помогает».
