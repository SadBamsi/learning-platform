> **Ответ за 30 секунд.** Компонент — функция, которая по `props` и `state` возвращает **описание** интерфейса (React-элементы — обычные объекты). Обновление проходит в две фазы: **render** (React вызывает компоненты, получает новое дерево элементов и сравнивает его с предыдущим — это и есть **reconciliation**) и **commit** (React применяет к DOM только найденные различия и запускает эффекты). Перерисовка компонента вызывается изменением его `state`, перерисовкой родителя или изменением контекста, который он читает. «Render» не равно «обновление DOM»: компонент может выполниться, а DOM останется нетронутым. Для сравнения списков React использует **`key`**: по нему он решает, это тот же элемент или новый. Поэтому ключ должен быть **стабильным и уникальным среди соседей** (id из данных), а не индексом, если список может меняться.

## Элементы, компоненты и «Virtual DOM»

Запись `<div className="x">hi</div>` после компиляции JSX превращается в вызов, который возвращает **обычный объект** — React-элемент. В режиме разработки он выглядит так:

```js
{
  $$typeof: Symbol(react.transitional.element),
  type: "div",
  key: null,
  props: { className: "x", children: "hi" },
  // плюс служебные поля разработческой сборки (_owner, _store)
}
```

Элемент — это **описание** («здесь должен быть `div` с такими свойствами»), а не DOM-узел и не экземпляр компонента. «Virtual DOM» — это просто дерево таких описаний в памяти. Компонент-функция вызывается React'ом; результатом вызова становится новое описание.

**Virtual DOM — не причина скорости.** Сравнение деревьев само по себе стоит ресурсов; прямой точечный `textContent = ...` быстрее. Ценность подхода в другом: вы пишете код как «интерфейс = функция от состояния» (декларативно), а React сам вычисляет минимальный набор изменений DOM и применяет его в одном месте. Верный ответ на собеседовании: «Это не про скорость, а про декларативность и предсказуемость; React избегает лишних DOM-операций, но сам рендер компонентов тоже не бесплатен».

## Две фазы: render и commit

1. **Render** — React вызывает функции компонентов (сверху вниз), строит новое дерево элементов и сравнивает его с предыдущим. В этой фазе **не должно быть побочных эффектов**: компонент обязан быть чистой функцией от `props`, `state` и контекста. Эта фаза в concurrent-режиме может быть прервана, отброшена и запущена заново.
2. **Commit** — React применяет найденные изменения к DOM (синхронно), затем вызывает эффекты.

Порядок внутри commit (проверено запуском): при первом монтировании вызовы идут «снизу вверх» — сначала `render Parent`, `render Child`, затем `useLayoutEffect` у `Child`, затем у `Parent`, потом `useEffect` у `Child` и `Parent`. При обновлении перед запуском новых эффектов сначала вызываются **все cleanup** предыдущих (сначала layout-эффектов, потом обычных).

```
render Parent → render Child        ← render (чистые вычисления)
layout Child → layout Parent        ← после изменения DOM, до отрисовки браузером
effect Child → effect Parent        ← после отрисовки (useEffect)
```

## Когда компонент перерисовывается

Три причины:

1. Изменилось **его собственное состояние** (`setState`, `dispatch`).
2. **Перерисовался родитель** — по умолчанию рендерятся **все** дочерние компоненты, даже если их `props` не менялись.
3. Изменилось значение **контекста**, который компонент читает (`useContext`).

Изменение `props` само по себе не «триггерит» рендер — оно лишь следствие того, что родитель перерисовался.

```jsx
function Parent() {
  const [n, setN] = useState(0);
  return (
    <div>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Child />        {/* пропсов нет, но Child всё равно перерисуется */}
    </div>
  );
}
```

Проверка: при клике логируются `Parent` и `Child`. Если обернуть `Child` в `React.memo`, он пропускается (см. тему про мемоизацию).

**Приём без `memo`: поднять «неизменяемую» часть как `children`.** Элемент `<Child />`, созданный снаружи и переданный пропсом, создаётся один раз в вышестоящем компоненте; когда `Counter` перерисовывается из-за своего состояния, он получает **тот же объект элемента**, и React видит, что ничего не изменилось. Проверено: при клике логируется только `Counter`.

```jsx
function Counter({ children }) {
  const [n, setN] = useState(0);
  return <div><button onClick={() => setN(n + 1)}>{n}</button>{children}</div>;
}
// <Counter><Child /></Counter>  — Child не перерисуется при клике
```

**Render ≠ обновление DOM.** Если после рендера результат для какого-то узла совпал с прошлым, React его не трогает. Поэтому лишний рендер часто невидим для пользователя, но стоит CPU.

## Reconciliation: как сравниваются деревья

Полное сравнение двух произвольных деревьев — O(n³). React использует **эвристики**, получая O(n):

1. **Элементы разных типов дают разные деревья.** Если на том же месте был `<div>`, а стал `<span>`, или был `<A />`, а стал `<B />`, React **уничтожает** старое поддерево (размонтирует, теряет состояние) и строит новое.
2. **Тот же тип на той же позиции — обновление.** DOM-узел или экземпляр компонента сохраняется, меняются только `props`; **состояние сохраняется**.
3. **Для списков идентичность задаёт `key`.**

Следствия, которые любят спрашивать:

```jsx
// Состояние Counter сохранится: тот же тип на той же позиции
flag ? <Counter /> : <Counter />

// Состояние сбросится: на той же позиции другой тип родителя (div)
flag ? <Counter /> : <div><Counter /></div>
```

Проверено: после двух кликов счётчик = 2; при переключении тернарника с тем же типом остаётся 2; при обёртке в `<div>` — 0.

Позиция в дереве важна: React отличает «первый ребёнок» от «второго». Поэтому условный рендер `{cond && <A />}` оставляет слот пустым, и позиции остальных элементов не сдвигаются.

### Сброс состояния через key

`key` можно ставить не только в списках. Изменение ключа у элемента заставляет React пересоздать его с нуля:

```jsx
<Profile key={userId} userId={userId} />   // при смене userId состояние формы сбросится
```

Это идиоматичный способ «обнулить» компонент при смене сущности (вместо `useEffect`, который вручную сбрасывает состояние).

### Анти-паттерн: компонент внутри компонента

```jsx
function Outer() {
  const [n, setN] = useState(0);
  const Inner = () => <input />;   // новая функция на каждый рендер = новый «тип»
  return <Inner />;
}
```

На каждом рендере `Inner` — **другая функция**, то есть другой тип. React размонтирует и монтирует его заново: теряется состояние, фокус в `input`, срабатывают эффекты. Проверено: `useState`-инициализатор `Inner` вызывается при каждом рендере `Outer`. Решение — объявить компонент **на верхнем уровне модуля**.

## Key в списках

```jsx
{todos.map((t) => <TodoItem key={t.id} todo={t} />)}
```

`key` нужен React, чтобы при изменении списка сопоставить старые и новые элементы: «этот элемент переехал», «этот удалён», «этот новый». Требования: ключ **уникален среди соседей** (не глобально) и **стабилен** между рендерами для одной и той же сущности.

**Почему нельзя `key={index}`, если список меняется (вставка, удаление, сортировка).** Ключ-индекс привязывает состояние не к сущности, а к позиции. Проверенный пример: три строки A, B, C, у каждой собственный `useState` для поля ввода. В A вводим текст, затем удаляем A.

```
key = index:  [ "B=typed-in-A", "C=" ]   ← текст остался у первой позиции, теперь это B
key = id:     [ "B=",           "C=" ]   ← состояние ушло вместе с A
```

Индекс допустим только для **статичных** списков, которые никогда не переупорядочиваются и не фильтруются.

Другие запреты:

- `key={Math.random()}` — ключ меняется на каждом рендере, все элементы пересоздаются (теряется состояние, DOM перестраивается).
- Ключ формируют из данных, а не в момент рендера: `crypto.randomUUID()` в рендере — тот же недостаток; id нужно присвоить при создании данных.

Если ключ не указан, React предупреждает в консоли (в dev) и по умолчанию использует индекс.

## StrictMode и двойной рендер

В разработке `<StrictMode>` вызывает функции компонентов (и инициализаторы состояния, редьюсеры) **дважды**, чтобы выявить нечистые вычисления; в production этого нет. Проверено: компонент логирует `render` дважды. Кроме того, при монтировании StrictMode один раз «эмулирует» размонтирование и повторное монтирование, чтобы найти эффекты без корректного cleanup (подробнее в теме про `useEffect`).

Если от двойного вызова что-то ломается — это сигнал, что рендер не чист (мутация внешних переменных, запрос в теле компонента).

## Fiber и конкурентность (кратко)

Начиная с React 16 reconciler построен на **Fiber**: работа над деревом разбита на мелкие единицы, которые можно приостановить. В React 18 это открыло concurrent-рендеринг (`useTransition`, `useDeferredValue`, Suspense): render-фазу можно прервать ради более срочного обновления. Именно поэтому render обязан быть чистым.

## Частые follow-up вопросы

**Перерисуется ли дочерний компонент, если пропсы не изменились?**
Да, если перерисовался родитель и ребёнок не обёрнут в `memo` (и не передан как `children`).

**Что хранится в Virtual DOM?**
Дерево React-элементов (описания), а не реальные узлы. Реальные узлы лежат в Fiber-дереве, которое React использует внутри.

**Почему нельзя вызывать `setState` в теле компонента (безусловно)?**
Это приведёт к бесконечному циклу «рендер → setState → рендер» (React выбросит ошибку о слишком большом числе рендеров). Допустима лишь точечная корректировка состояния по условию, но обычно лучше вычислять значение прямо в рендере.

**Как сбросить состояние дочернего компонента при смене сущности?**
Менять `key`.

**Зависит ли порядок рендера дочерних компонентов от порядка в JSX?**
Рендер идёт сверху вниз, слева направо по порядку в дереве; но полагаться на это нельзя: компонент должен быть независим от порядка.

## Типичные ошибки

- Ожидать, что рендер = обновление DOM, и наоборот.
- `key={index}` в списках, которые меняются.
- Объявлять компоненты внутри других компонентов.
- Менять `props`, `state` или внешние переменные прямо в рендере.
- Путать `key` и `props`: `key` не доступен внутри компонента как `props.key`.
- Считать, что `memo` везде нужен «на всякий случай» (см. тему про мемоизацию).
