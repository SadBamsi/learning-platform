> **Ответ за 30 секунд.** `state` — данные, которые React хранит между рендерами компонента; изменение через `setState` ставит в очередь новый рендер. Значение состояния в рендере — **снимок**: внутри одного рендера и всех его замыканий переменная `n` не меняется, даже если вы вызвали `setN(n + 1)`. React **батчит** несколько обновлений в один рендер (в React 18+ в любых контекстах, включая `setTimeout` и промисы). Если новое значение зависит от предыдущего, используйте **функциональную форму** `setN(prev => prev + 1)`. Состояние нельзя **мутировать**: React сравнивает значения через `Object.is`, поэтому для объектов и массивов нужно создавать новые копии. Не дублируйте в состоянии то, что можно вычислить из props или другого состояния, и держите состояние как можно ближе к тем, кто его использует; если оно нужно нескольким компонентам, поднимайте его к ближайшему общему предку. Для связанных переходов состояния удобен `useReducer`.

## State как снимок

Каждый рендер компонента получает **свои** значения `props` и `state`. Обработчики событий, созданные в этом рендере, «видят» именно их.

```jsx
function Counter() {
  const [n, setN] = useState(0);
  return (
    <button onClick={() => {
      setN(n + 1);
      console.log(n);   // всё ещё 0: переменная n в этом рендере не изменится
    }}>{n}</button>
  );
}
```

`setN` не меняет переменную `n`; он **планирует** новый рендер, в котором `useState` вернёт новое значение. Поэтому формулировка «`setState` асинхронный» не совсем точна: правильнее «обновления **батчатся** и применяются при следующем рендере; значение в текущем рендере не меняется».

Тот же эффект в таймерах: колбэк `setTimeout`, созданный в рендере с `n = 0`, залогирует `0`, даже если за время ожидания пользователь нажал кнопку ещё раз (проверено: лог `[0]`, при этом на экране уже `2`).

## Батчинг и функциональные обновления

React собирает несколько вызовов `setState` в рамках одного события и делает **один** рендер.

```jsx
setN(n + 1);
setN(n + 1);
setN(n + 1);          // результат: n + 1 (все три используют один и тот же снимок n)

setN((prev) => prev + 1);
setN((prev) => prev + 1);
setN((prev) => prev + 1);   // результат: n + 3
```

Проверено: с исходным `0` первый вариант даёт `1`, второй — `3`.

Очередь обновлений обрабатывается по порядку: `setN(n + 5); setN(x => x + 1)` из `0` даёт `6`; `setN(n + 5); setN(x => x + 1); setN(42)` даёт `42` (последнее значение побеждает).

**Автоматический батчинг (React 18).** До React 18 обновления батчились только внутри обработчиков событий React. С `createRoot` батчинг работает **везде**: в `setTimeout`, промисах, нативных обработчиках. Проверено: два `setState` внутри `setTimeout` дают один рендер. Если вам нужно применить обновление к DOM синхронно, есть `flushSync` из `react-dom`, но это редкий случай.

**Когда нужна функциональная форма:** новое значение зависит от предыдущего (счётчики, добавление в массив), особенно в асинхронных колбэках и в `useEffect`, где замыкание может хранить устаревшее значение.

## Иммутабельность

React сравнивает новое значение с прежним через `Object.is`. Если они равны, обновление **пропускается**: при `setN(0)` в состоянии `0` рендера не будет (проверено).

Поэтому с объектами и массивами нужно создавать **новую ссылку**:

```jsx
const [user, setUser] = useState({ name: "Ann", address: { city: "Minsk" } });

// плохо: мутация, ссылка та же → рендера нет, UI не обновится
user.name = "Bob";
setUser(user);

// хорошо
setUser({ ...user, name: "Bob" });
setUser({ ...user, address: { ...user.address, city: "Brest" } });   // вложенные объекты тоже копируем
```

Проверено: после `o.n++; setO(o)` компонент не перерисовывается и на экране остаётся `0`, хотя в объекте уже `1`. С `setO({ ...o, n: o.n + 1 })` — один рендер и `1`.

Операции над массивами:

| Действие | Мутирует (нельзя) | Иммутабельно |
|---|---|---|
| Добавить | `push`, `unshift` | `[...arr, x]` |
| Удалить | `splice`, `pop` | `arr.filter(...)` |
| Заменить | `arr[i] = x` | `arr.map(...)` |
| Сортировка | `sort`, `reverse` | `[...arr].sort()`, `toSorted()` |

Почему это важно, помимо перерисовки: `memo`, `useMemo`, `useEffect` и `useCallback` сравнивают зависимости по ссылке; без новых ссылок они не заметят изменений. Иммутабельные данные также упрощают отладку (например, «путешествие по времени» в Redux DevTools) и делают поведение предсказуемым: старый снимок состояния остаётся неизменным. Для глубоко вложенных структур используют **Immer** (`useImmerReducer`, в Redux Toolkit встроен).

## Инициализация и значения-функции

```jsx
const [a, setA] = useState(expensive());        // expensive вызывается на КАЖДОМ рендере (результат игнорируется)
const [b, setB] = useState(() => expensive());  // ленивая инициализация: один раз при монтировании
```

Проверено: за два повторных рендера `expensive()` в первом варианте вызывается дважды, во втором — ни разу. Пользуйтесь ленивой формой для дорогих вычислений и чтения из `localStorage`.

Если нужно сохранить **функцию** как значение состояния, оберните: `useState(() => myFn)` и `setF(() => newFn)`. Иначе React примет её за инициализатор или обновление.

## Производное состояние: не хранить лишнее

Если значение можно **вычислить** из props или другого состояния, не заводите для него отдельный `useState` и не синхронизируйте через `useEffect`:

```jsx
// плохо: два источника правды, лишний рендер, возможна рассинхронизация
const [items, setItems] = useState([]);
const [visible, setVisible] = useState([]);
useEffect(() => setVisible(items.filter((i) => i.active)), [items]);

// хорошо: вычисляем при рендере (при необходимости — useMemo)
const visible = items.filter((i) => i.active);
```

**Копирование props в state** — частая ошибка: `useState(props.initial)` читает значение **только при монтировании**. Проверено: если `initial` сменился с 1 на 2, на экране остаётся `1`. Либо вычисляйте из props прямо в рендере, либо (если нужно именно «начальное значение, потом пользователь меняет сам») называйте проп `initialValue` и при смене сущности пересоздавайте компонент через `key`.

Минимальное состояние: храните **id выбранного элемента**, а не копию объекта, иначе при обновлении списка копия устареет.

## Где держать состояние

1. **Рядом с использованием** (colocation) — чем локальнее, тем меньше перерисовок и проще код.
2. **Подъём состояния** (lifting state up): если два компонента должны быть синхронны, переносим состояние в ближайшего общего родителя и передаём вниз значение и обработчик. Так «источник правды» один.
3. Если пропсы приходится протаскивать через много уровней — **контекст** или внешний стор (см. тему про state management).
4. Данные с сервера — не «обычное» состояние: для них используют TanStack Query / SWR / RSC (см. отдельную тему).

## useReducer

```jsx
function cartReducer(state, action) {
  switch (action.type) {
    case "add":    return { ...state, items: [...state.items, action.item] };
    case "remove": return { ...state, items: state.items.filter((i) => i.id !== action.id) };
    case "clear":  return { ...state, items: [] };
    default: throw new Error(`Unknown action: ${action.type}`);
  }
}

const [cart, dispatch] = useReducer(cartReducer, { items: [] });
dispatch({ type: "add", item });
```

Когда `useReducer` лучше `useState`:

- состояние — объект со связанными полями, и переходы между ними нетривиальны;
- следующее состояние зависит от предыдущего по нескольким сценариям;
- нужно легко тестировать логику: редьюсер — **чистая функция** `(state, action) => newState`, её тестируют без React;
- нужно передать вниз один стабильный `dispatch` вместо набора колбэков (`dispatch` не меняется между рендерами).

Редьюсер не должен делать побочных эффектов и мутировать состояние.

## Частые follow-up вопросы

**`setState` синхронный или асинхронный?**
Он не меняет значение в текущем рендере и батчится. Новое значение вы увидите в следующем рендере.

**Как получить актуальное значение сразу после `setState`?**
Вычислить его заранее (`const next = n + 1; setN(next); use(next)`) или использовать функциональное обновление / `useEffect` по значению.

**Что будет, если вызвать `setState` с тем же значением?**
`Object.is` вернёт `true`, React пропустит обновление. В некоторых случаях он может один раз вызвать компонент перед пропуском, но дочерние компоненты не перерисуются.

**Можно ли использовать несколько `useState`?**
Да. Группируйте поля, которые меняются вместе, в один объект или `useReducer`; независимые значения держите отдельно.

**Почему состояние сбрасывается при смене порядка/типа компонентов?**
Состояние привязано к позиции в дереве и типу компонента (см. тему про рендеринг).

**Чем состояние отличается от обычной переменной и от `ref`?**
Обычная переменная сбрасывается при каждом рендере и не вызывает его; `ref` сохраняется между рендерами, но его изменение рендер **не** вызывает; `state` — и сохраняется, и вызывает рендер.

## Типичные ошибки

- Мутация состояния (`push`, `obj.x = ...`) с последующим `setState` той же ссылки.
- Использование `setN(n + 1)` несколько раз подряд и ожидание `+3`.
- Чтение состояния сразу после `setState` и ожидание нового значения.
- Копия props в состоянии без понимания, что она не обновляется.
- Дублирование данных в нескольких `useState`, которые нужно синхронизировать.
- Хранение вычисляемых значений в `useState` + `useEffect`.
- Хранение копии выбранного объекта вместо его id.
