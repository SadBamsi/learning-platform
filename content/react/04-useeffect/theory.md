> **Ответ за 30 секунд.** `useEffect` — способ **синхронизировать компонент с внешней системой** (сеть, подписки, таймеры, DOM-API, сторонние библиотеки) *после* того, как React отрисовал изменения. Это не «componentDidMount + componentDidUpdate»: эффект описывает, **как начать** синхронизацию, а возвращаемая функция **cleanup** — как её **остановить**. Эффект запускается после рендера; если указан массив зависимостей, — только когда они изменились (сравнение через `Object.is`); `[]` — один раз при монтировании; без массива — после каждого рендера. Перед повторным запуском и при размонтировании вызывается cleanup. В разработке `StrictMode` специально делает «монтирование → cleanup → монтирование», чтобы выявить забытый cleanup. Частые ловушки: устаревшие значения (stale closure), **гонки запросов** (старый ответ приходит позже нового), бесконечные циклы из-за новых объектов в зависимостях и использование эффектов там, где хватило бы вычисления при рендере или обработчика события.

## Модель: синхронизация, а не жизненный цикл

```jsx
useEffect(() => {
  const connection = createConnection(roomId);   // начать синхронизацию
  connection.connect();
  return () => connection.disconnect();           // остановить синхронизацию
}, [roomId]);                                     // перезапускать при смене roomId
```

Правильный вопрос — не «когда это запускается», а «**с чем** я синхронизируюсь и от **каких значений** это зависит». Компонент может монтироваться, обновляться и размонтироваться; эффект просто описывает «пока roomId такой, соединение такое».

Порядок (проверено запуском) для `<C id={1} />` → повторный рендер с тем же `id` → `id={2}` → размонтирование:

```
effect 1
(тот же id: эффект не запускается)
cleanup 1
effect 2
cleanup 2          ← при размонтировании
```

## Массив зависимостей

| Запись | Когда запускается |
|---|---|
| `useEffect(fn)` | после **каждого** рендера |
| `useEffect(fn, [])` | один раз после монтирования (и cleanup при размонтировании) |
| `useEffect(fn, [a, b])` | после монтирования и при каждом изменении `a` или `b` |

Зависимости — это **все реактивные значения**, которые читает эффект: `props`, `state`, переменные и функции, объявленные в компоненте. Их не «выбирают», они определяются кодом эффекта; линтер `exhaustive-deps` помогает не пропустить.

Сравнение идёт через `Object.is`. Поэтому **объекты, массивы и функции, создаваемые в теле компонента, при каждом рендере новые**, и эффект перезапускается каждый раз:

```jsx
const options = { room: roomId };               // новый объект на каждый рендер
useEffect(() => { connect(options); }, [options]);   // ✖ запуск на каждом рендере
```

Проверено: при двух повторных рендерах эффект запустился дважды. Исправления: создавать объект **внутри эффекта**, зависеть от примитивов (`roomId`), оборачивать в `useMemo`/`useCallback` или вынести за пределы компонента.

Если эффект вызывает `setState` с новым объектом и зависит от него, получится **бесконечный цикл**: эффект → setState → рендер → новый объект → эффект.

## Cleanup и StrictMode

Cleanup вызывается:

- **перед** следующим запуском эффекта (при изменении зависимостей);
- при **размонтировании**.

В разработке `<StrictMode>` один раз при монтировании выполняет: `effect → cleanup → effect`. Проверено: лог `[effect, cleanup, effect]`. В production этого нет. Смысл — гарантировать, что эффект можно остановить и запустить снова без побочных последствий: React вправе это делать и в реальной работе (например, когда параметр меняется и эффект пересоздаётся).

Пример бага, который так обнаруживается: подписка без отписки.

```jsx
useEffect(() => {
  const onResize = () => setW(window.innerWidth);
  window.addEventListener("resize", onResize);
  // нет return () => window.removeEventListener("resize", onResize)
}, []);
```

Проверено: в StrictMode после монтирования остаётся **2** слушателя, после размонтирования — по-прежнему 2 (утечка). С cleanup: 1 после монтирования, 0 после размонтирования.

Правило: если эффект запускается дважды и ломается — нужно исправить cleanup, а не «защищаться от двойного вызова» флагом `didRun`.

## Запросы данных и race condition

```jsx
useEffect(() => {
  fetch(`/api/user/${id}`).then((r) => r.json()).then(setUser);
}, [id]);
```

Проблема: пользователь быстро переключил `id` с 1 на 2. Запрос для `1` может завершиться **позже** запроса для `2` и перезаписать правильные данные. Проверено на имитации (запрос для `1` — 120 мс, для `2` — 20 мс): без защиты на экране остаётся `data-1`.

Решения:

```jsx
// 1. Флаг игнорирования устаревшего ответа
useEffect(() => {
  let ignore = false;
  fetchUser(id).then((u) => { if (!ignore) setUser(u); });
  return () => { ignore = true; };
}, [id]);

// 2. AbortController — отменяет сам запрос
useEffect(() => {
  const ac = new AbortController();
  fetch(`/api/user/${id}`, { signal: ac.signal })
    .then((r) => r.json())
    .then(setUser)
    .catch((e) => { if (e.name !== "AbortError") setError(e); });
  return () => ac.abort();
}, [id]);
```

Проверено: с флагом на экране `data-2`; с `AbortController` запрос для `1` отменён (`aborted 1`), на экране `data-2`.

Дополнительно нужны состояния `loading` и `error`. Ручная реализация легко содержит ошибки (кэш, повторные запросы, дедупликация, повторные попытки), поэтому в реальных проектах данные с сервера получают через **TanStack Query / SWR** или средства фреймворка (в Next.js — серверные компоненты и `fetch` на сервере), а не «голый» `useEffect`.

**`async` в эффекте.** Нельзя писать `useEffect(async () => {...})`: `async`-функция возвращает Promise, а React ожидает функцию cleanup или ничего. Проверено: React предупреждает «must not return anything besides a function, which is used for clean-up». Объявляйте `async`-функцию внутри и вызывайте её.

## Когда эффект не нужен

Эффекты — «запасной выход» для синхронизации с внешним миром. Не используйте их для:

1. **Производных данных.** Если значение вычисляется из `props`/`state`, считайте его при рендере (`useMemo` — только если дорого). Проверено: вариант «эффект + `setState`» даёт 2 рендера, вычисление при рендере — 1.
2. **Реакции на действие пользователя.** Если код должен выполниться «потому что пользователь нажал», его место — **обработчик события**, а не эффект на изменение состояния.
3. **Сброса состояния при смене пропса.** Используйте `key` (см. тему про рендеринг): проверено, что сброс через эффект даёт промежуточный рендер со старым текстом (`effect:2:typed`), затем пустой.
4. **Цепочек эффектов**, где один эффект меняет состояние ради другого.
5. **Уведомления родителя**: вызывайте колбэк в обработчике, а не в эффекте по изменению состояния.
6. **Подписки на внешние хранилища**: вместо ручного `useEffect + useState` есть `useSyncExternalStore`.
7. **Инициализации приложения** (однократные действия при старте) — выносите на уровень модуля или в точку входа.

## useEffect против useLayoutEffect

- `useEffect` — вызывается **после** того, как браузер отрисовал кадр (обычно); не блокирует отображение.
- `useLayoutEffect` — вызывается **сразу после изменений DOM, до отрисовки**; позволяет синхронно измерить DOM (`getBoundingClientRect`) и поправить его без «мигания». Блокирует отрисовку, поэтому используется редко.

Порядок при монтировании (проверено): `render Parent → render Child → layout Child → layout Parent → effect Child → effect Parent`. На сервере (при SSR) эффекты не выполняются вообще: измерения DOM возможны только в браузере.

Также существует `useInsertionEffect` (для библиотек CSS-in-JS: вставка стилей до остальных эффектов).

## Частые follow-up вопросы

**Почему эффект запускается дважды в разработке?**
Это `StrictMode`: он проверяет, что эффект корректно останавливается cleanup'ом. В production двойного запуска нет.

**Как выполнить код только один раз при монтировании?**
`useEffect(() => {...}, [])` — но cleanup всё равно должен быть корректным. Если нужно «один раз за всю жизнь приложения» (аналитика, инициализация), это выносят из компонента.

**Можно ли `setState` в эффекте?**
Можно, но часто это признак, что значение надо вычислить при рендере; лишний `setState` даёт дополнительный рендер.

**Что будет, если не указать зависимости, но использовать `state` внутри эффекта?**
Если массив пропущен целиком — эффект работает на каждом рендере и видит свежие значения; если указан `[]` — получите stale closure.

**Как отменить запрос?**
`AbortController`; для устаревших ответов без отмены — флаг `ignore` в cleanup.

**Почему эффект не получает значения «будущего» рендера?**
Он замыкается на значениях того рендера, в котором создан; при изменении зависимостей создаётся новый эффект.

## Типичные ошибки

- Забытый cleanup (таймеры, подписки, соединения).
- `[]` при использовании реактивных значений внутри эффекта.
- Объект/функция из тела компонента в зависимостях.
- `async` функция напрямую в `useEffect`.
- Запрос без защиты от гонок и без `loading`/`error`.
- Эффект вместо вычисления при рендере или обработчика события.
- Отключение `exhaustive-deps` вместо исправления причины.
- «Защита» от двойного запуска в StrictMode флагом вместо корректного cleanup.
