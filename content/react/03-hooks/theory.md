> **Ответ за 30 секунд.** Хуки — функции (`useState`, `useEffect`, `useRef`…), которые позволяют функциональному компоненту хранить состояние и подключаться к жизненному циклу. Два правила: вызывать их **только на верхнем уровне** компонента или другого хука (не в условиях, циклах и вложенных функциях) и **только из компонентов или кастомных хуков**. Причина: React не знает «имён» хуков и сопоставляет состояние **по порядку вызова** в каждом рендере, поэтому порядок должен быть одинаковым. Вторая классика — **замыкания**: каждый рендер создаёт свои функции, которые «запоминают» `props` и `state` своего рендера; в долгоживущих колбэках (таймеры, подписки, эффекты с неполными зависимостями) получается **устаревшее значение** (stale closure). Лечится функциональным обновлением, правильными зависимостями, `ref` с актуальной функцией или `useEffectEvent` (React 19.2+).

## Что именно спрашивают

- «Почему хуки нельзя вызывать в условиях и циклах?»
- «Как React понимает, какое состояние принадлежит какому `useState`?» («Напишите упрощённую реализацию `useState`»)
- «Что такое stale closure? Приведите пример и способы исправления».
- «Могут ли два компонента, использующих один кастомный хук, делиться состоянием?»
- «Зачем нужен линтер `react-hooks` и правила `rules-of-hooks`, `exhaustive-deps`?»
- «Чем хуки лучше классов? Что они не умеют?»

## Правила хуков

1. **Вызывайте хуки только на верхнем уровне**: не внутри `if`, циклов, вложенных функций, `try/catch`, после раннего `return`.
2. **Вызывайте хуки только из функциональных компонентов или из кастомных хуков** (функций, имя которых начинается с `use`).

```jsx
function Bad({ show }) {
  if (show) {
    const [a, setA] = useState(0);   // ✖ условный вызов
  }
  const [b, setB] = useState(1);
  // ...
}
```

Проверено запуском: при переходе `show` с `false` на `true` React сообщает в консоль «React has detected a change in the order of Hooks» и выбрасывает «Rendered more hooks than during the previous render». Вызов хука вне компонента даёт «Invalid hook call».

Исключение из «хуков» — функция **`use`** (React 19): она технически не хук и **может** вызываться в условиях и циклах (проверено: условное чтение контекста через `use(Ctx)` работает).

## Почему именно так: как устроены хуки внутри

React хранит состояние хуков компонента **списком, привязанным к его узлу в дереве** (Fiber). При рендере он идёт по списку **по порядку вызова**: первый `useState` получает первую ячейку, второй — вторую и так далее. Идентификатора у хука нет — только позиция. Если порядок меняется, ячейки «съезжают», и состояние достаётся не тому хуку.

Упрощённая модель (то, что часто просят написать на собеседовании):

```js
let hooks = [];     // массив ячеек состояния текущего компонента
let idx = 0;        // индекс текущего хука в этом рендере

function useState(initial) {
  const i = idx++;
  if (!(i in hooks)) hooks[i] = initial;
  const setState = (v) => {
    hooks[i] = typeof v === "function" ? v(hooks[i]) : v;
    render();       // планируем новый рендер
  };
  return [hooks[i], setState];
}

function render() {
  idx = 0;          // каждый рендер начинаем с первой ячейки
  return App();
}
```

Проверено: два `useState` в `App` получают независимые ячейки, `setA(v => v + 1)` и `setB("y")` дают `[1, "y"]`. Реальная реализация сложнее (очереди обновлений, приоритеты, связный список вместо массива), но идея та же: **порядок вызовов = идентичность хука**.

Отсюда следствия:

- Условный вызов или цикл с переменным числом итераций ломает соответствие.
- Каждый **вызов** кастомного хука получает свои ячейки. Два компонента с `useCounter()` **не делят состояние**: проверено, клик по первому счётчику не влияет на второй. Чтобы делиться, используют контекст или внешнее хранилище.
- Если условие нужно, помещайте его **внутрь** хука или выносите ветку в отдельный компонент.

Правила проверяет плагин **`eslint-plugin-react-hooks`**: `rules-of-hooks` (ошибка) и `exhaustive-deps` (предупреждение о неполных зависимостях). Отключать их без понимания причины опасно.

## Замыкания: каждый рендер — «своя копия» значений

Функция компонента вызывается заново на каждый рендер; все функции, созданные внутри, запоминают значения `props` и `state` **этого** рендера.

```jsx
function Counter() {
  const [n, setN] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(n);      // всегда 0!
      setN(n + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []);                  // эффект запущен один раз в рендере, где n = 0

  return <p>{n}</p>;
}
```

Эффект создан в самом первом рендере, где `n === 0`, и из-за пустого массива зависимостей никогда не пересоздаётся. Колбэк таймера навсегда запомнил `n = 0`: на экране остаётся `1` (каждый тик ставит `0 + 1`). Проверено: лог `[0, 0, 0, 0]`, на экране `1`.

### Способы исправления

**1. Функциональное обновление** — если нужно только изменить состояние на основе предыдущего:

```jsx
setInterval(() => setN((prev) => prev + 1), 1000);   // замыкание n не нужно
```

**2. Указать зависимости** — эффект пересоздаётся при каждом изменении `n`:

```jsx
useEffect(() => {
  const id = setInterval(() => setN(n + 1), 1000);
  return () => clearInterval(id);
}, [n]);
```

Верно, но интервал перезапускается на каждом тике (в примере с таймером это может быть нежелательно: сбивается отсчёт).

**3. `ref` с актуальной функцией** (паттерн Дэна Абрамова `useInterval`):

```jsx
function useInterval(callback, delay) {
  const saved = useRef(callback);
  useEffect(() => { saved.current = callback; });          // всегда свежая функция

  useEffect(() => {
    if (delay === null) return;                            // null — пауза
    const id = setInterval(() => saved.current(), delay);  // интервал не пересоздаётся
    return () => clearInterval(id);
  }, [delay]);
}
```

Проверено: значения в колбэке `[0, 1, 2, 3, 4]`, интервал создаётся один раз, пауза через `delay = null` работает.

**4. `useEffectEvent` (React 19.2+).** Выносит «событийную» часть из эффекта: функция всегда видит свежие `props`/`state`, но не входит в зависимости.

```jsx
function Timer() {
  const [n, setN] = useState(0);
  const tick = useEffectEvent(() => setN(n + 1));      // всегда актуальный n
  useEffect(() => {
    const id = setInterval(() => tick(), 1000);
    return () => clearInterval(id);
  }, []);                                              // tick в зависимости не добавляют
}
```

Ограничения (по документации React): вызывать Effect Event можно только изнутри эффектов (и других Effect Event); не передавать его в другие компоненты и хуки; не использовать, чтобы «заглушить» линтер для обычных зависимостей. Идентичность функции меняется на каждом рендере.

### Другие проявления замыканий

- **Отложенные колбэки**: `setTimeout(() => alert(count), 3000)` покажет значение на момент клика, даже если потом оно изменилось (проверено: снимок `a`, через `ref.current` — актуальное `b`). Иногда именно такое поведение нужно (показать то, что видел пользователь), иногда нет.
- **Обработчики событий, переданные подписке** (`addEventListener`, WebSocket) в эффекте с `[]`.
- **`useCallback`/`useMemo` с неполными зависимостями** возвращают старую функцию/значение.

**Золотое правило:** все реактивные значения (`props`, `state`, значения, вычисленные из них), которые читает эффект или мемоизированный колбэк, должны быть в массиве зависимостей. Если из-за этого эффект «слишком часто» срабатывает — это сигнал изменить структуру кода (функциональное обновление, `ref`, `useEffectEvent`, вынос в обработчик), а не отключить линтер.

## Основные хуки

| Хук | Для чего |
|---|---|
| `useState`, `useReducer` | состояние |
| `useEffect`, `useLayoutEffect` | синхронизация с внешним миром, побочные эффекты |
| `useRef` | значение, не вызывающее рендер; доступ к DOM |
| `useMemo`, `useCallback` | мемоизация значения/функции |
| `useContext` (и `use`) | чтение контекста |
| `useId` | стабильные id (SSR) |
| `useTransition`, `useDeferredValue` | приоритеты обновлений |
| `useSyncExternalStore` | подписка на внешний стор |
| `useActionState`, `useOptimistic`, `useFormStatus` | формы и Actions (React 19) |

## Частые follow-up вопросы

**Могут ли два компонента делить состояние через один кастомный хук?**
Нет: каждый вызов хука создаёт собственное состояние. Для общего — контекст или внешний стор.

**Почему кастомный хук должен начинаться с `use`?**
Это соглашение, по которому линтер понимает, что внутри можно вызывать хуки, и применяет к функции правила хуков. React сам имя не проверяет.

**Можно ли вызвать хук внутри обработчика события?**
Нет. Обработчик выполняется вне рендера; нужные значения получают на верхнем уровне компонента и используют в обработчике.

**Что делать, если условно нужно использовать хук?**
Выделить ветку в отдельный компонент (и рендерить его условно) либо всегда вызывать хук, а условие проверять внутри него.

**Чем хуки лучше классов?**
Логику можно переиспользовать (кастомные хуки) без HOC и render props, связанный код не разбросан по методам жизненного цикла, нет `this`. Недостатки: замыкания (stale closure), строгая дисциплина зависимостей, нет аналога `componentDidCatch` (границы ошибок пока классы).

**Что такое «ленивая инициализация»?**
`useState(() => compute())` — функция вызывается один раз при монтировании.

## Типичные ошибки

- Хуки в условиях, циклах, после раннего `return`, внутри обработчиков.
- Пустой массив зависимостей «чтобы работало один раз» при чтении `state`/`props` внутри эффекта.
- Отключение `exhaustive-deps` вместо исправления причины.
- Передача `useEffectEvent`-функции в дочерний компонент или в массив зависимостей.
- Ожидание, что кастомный хук разделяет состояние между компонентами.
- Мутация `ref.current` во время рендера в сценариях, где результат должен влиять на вывод (используйте `state`).
