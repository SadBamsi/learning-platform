> **Ответ за 30 секунд.** Оптимизацию начинают с **измерений**, а не с `memo`: React DevTools Profiler (почему и сколько рендерился компонент), вкладка Performance браузера (долгие задачи, layout, paint), production-сборка (в dev React медленнее и делает двойные рендеры) и метрики пользователя (**LCP, INP, CLS**). Дальше — по убыванию эффекта: (1) **уменьшить объём работы**: данные, DOM, размер бандла (code splitting через `lazy` + `Suspense`, виртуализация длинных списков); (2) **убрать лишние рендеры**: состояние ближе к месту использования, `children`, стабильные ссылки + `memo`, раздельные контексты, React Compiler; (3) **не блокировать главный поток**: `useTransition`/`useDeferredValue`, вынос тяжёлых вычислений (Web Worker), debounce/throttle высокочастотных событий; (4) **ускорить загрузку**: SSR/RSC, оптимизация изображений и шрифтов, кэширование. Типичная ошибка — мемоизировать «на всякий случай» без замера.

## Шаг 0: измерить

1. **Production-сборка.** Dev-режим добавляет проверки и двойной рендер в StrictMode; замеры в нём вводят в заблуждение.
2. **React DevTools Profiler.** Запишите сессию (клик, ввод): он показывает, какие компоненты рендерились, **сколько** это заняло и **почему** (изменились props/state/hooks/контекст — нужно включить «Record why each component rendered»). Также помогает «Highlight updates when components render».
3. **`<Profiler id onRender>`** — программный замер. Колбэк получает `id`, `phase` (`mount`/`update`), `actualDuration` (время рендера поддерева в этом коммите) и `baseDuration` (оценка времени рендера без мемоизации). Проверено: колбэк вызывается при монтировании и обновлении, значения числовые. Если `actualDuration` заметно меньше `baseDuration`, мемоизация работает.
4. **Вкладка Performance браузера.** Ищите **Long Tasks** (> 50 мс), пересчёты layout и перерисовку. Узкое место не всегда React: иногда это тяжёлый CSS, огромный DOM или сторонний скрипт.
5. **Метрики.** *LCP* (скорость показа основного контента; ориентир по web.dev ≤ 2,5 с), *INP* (отзывчивость на действия пользователя; ≤ 200 мс; заменил FID среди Core Web Vitals), *CLS* (сдвиги макета; ≤ 0,1).

## Уменьшить объём работы

### Виртуализация списков

Не рендерите 10 000 строк: отрисуйте только видимые. Готовые решения — `@tanstack/react-virtual`, `react-window`. Идея простейшей реализации (фиксированная высота строки):

```jsx
const ROW = 20, VIEW = 100;

function VirtualList({ items }) {
  const [top, setTop] = useState(0);
  const start = Math.max(0, Math.floor(top / ROW) - 2);                  // небольшой запас
  const end = Math.min(items.length, Math.ceil((top + VIEW) / ROW) + 2);

  return (
    <div style={{ height: VIEW, overflow: "auto" }} onScroll={(e) => setTop(e.currentTarget.scrollTop)}>
      <div style={{ height: items.length * ROW, position: "relative" }}>
        {items.slice(start, end).map((item, i) => (
          <div key={item} style={{ position: "absolute", top: (start + i) * ROW, height: ROW }}>{item}</div>
        ))}
      </div>
    </div>
  );
}
```

Проверено на 1000 элементов: в DOM 7 строк у верха списка и 9 после прокрутки на `scrollTop = 5000` (строки с 248 по 256). Ограничения: нужна высота строк (фиксированная или измеряемая), ломается поиск по странице (`Ctrl+F`) и доступность — нужны `aria`-атрибуты (`aria-rowcount`, роль списка).

Альтернативы: пагинация, «показать ещё», бесконечная прокрутка с ограничением числа страниц в памяти.

### Размер бандла и code splitting

```jsx
const Chart = lazy(() => import("./Chart"));      // тяжёлый компонент загрузится отдельным чанком

<Suspense fallback={<Spinner />}>
  {showChart && <Chart />}
</Suspense>
```

Проверено: чанк не загружается, пока компонент не отрисован; в момент показа виден `fallback`, после загрузки — компонент. Что выносить: маршруты (в Next.js разбиение по страницам автоматическое), модалки, редкие экраны, тяжёлые библиотеки (редакторы, графики). Загрузку можно **упреждать**: начинать `import()` по `onMouseEnter` кнопки или после простоя.

Инструменты анализа бандла: визуализаторы (`@next/bundle-analyzer`, `rollup-plugin-visualizer`, `source-map-explorer`). Типичные «жиры»: целиком подключённый `lodash` (используйте импорт отдельных функций или `lodash-es`), `moment` (замена: `date-fns`/`dayjs`), дубли зависимостей разных версий, неиспользуемый код (tree-shaking работает с ES-модулями).

## Убрать лишние рендеры

Порядок действий (подробности — в темах про рендеринг, состояние и мемоизацию):

1. Опустить состояние вниз; тяжёлое передавать как `children`.
2. Не создавать компоненты внутри компонентов; ключи — стабильные id.
3. Не держать в состоянии производные данные; вычислять при рендере.
4. `memo` + стабильные ссылки (`useCallback`/`useMemo`) там, где Profiler показывает дорогой повторный рендер.
5. Разделять контексты; для часто меняющегося состояния — стор с selector.
6. Включить React Compiler (если проект готов к его правилам).

## Высокочастотные события

`mousemove`, `scroll`, `resize`, ввод в поле. Каждый `setState` — рендер.

- **Не нужно перерисовывать React** — меняйте DOM напрямую через `ref` или CSS-переменные. Проверено: при 5 событиях `mousemove` вариант с `state` дал 5 рендеров, вариант с `ref` и прямой записью в DOM — 0.
- **Debounce** (выполнить после паузы) — для поиска по вводу; **throttle** или `requestAnimationFrame` — для прокрутки/движения (не чаще раза за кадр).
- **Пассивные слушатели** (`{ passive: true }`) для `scroll`/`touch`.
- Анимации — через CSS (`transform`, `opacity`), которые обрабатывает композитор, а не через изменение состояния на каждом кадре.

## Не блокировать главный поток

- **`useTransition` / `useDeferredValue`**: пометить тяжёлое обновление как несрочное, чтобы ввод оставался отзывчивым (подробнее — в теме про concurrent rendering).
- **Web Worker** для тяжёлых вычислений (парсинг больших данных, сжатие, криптография).
- Разбиение долгой синхронной работы на куски (`setTimeout`/`scheduler.yield`, где доступен).
- Для данных — стриминг и `Suspense`, чтобы показывать часть интерфейса раньше.

## Загрузка и сеть

- **SSR/SSG/RSC** — отдавать готовый HTML (быстрее LCP); подробно в разделе про Next.js.
- **Изображения**: современные форматы (WebP/AVIF), правильные размеры, `loading="lazy"` для невидимых, явные `width`/`height` (против CLS), `fetchPriority="high"` (в JSX) для LCP-картинки. В Next.js — компонент `next/image`.
- **Шрифты**: `font-display`, предзагрузка, подмножества (`next/font`).
- **Кэширование**: заголовки `Cache-Control`, CDN, кэш данных на клиенте (TanStack Query).
- Меньше запросов: пакетная загрузка, предзагрузка критичных данных, уменьшение «водопадов» (последовательных запросов).

## Чек-лист при тормозящем интерфейсе

1. Воспроизвести в production-сборке и записать профиль.
2. Определить тип проблемы: **JS** (долгие рендеры/вычисления), **DOM** (слишком много узлов), **сеть** (большой бандл, водопады), **layout/paint**.
3. Исправить самое дорогое и **перемерить**. Каждое улучшение подтверждать числом.
4. Зафиксировать результат: бюджет бандла в CI, Lighthouse CI, мониторинг реальных пользователей (RUM).

## Частые follow-up вопросы

**Почему приложение медленнее в dev-режиме?**
Включены дополнительные проверки, предупреждения, StrictMode с двойным рендером, нет минификации и оптимизаций. Для замеров нужна production-сборка.

**Что такое `baseDuration`?**
Оценка времени рендера всего поддерева без мемоизации; сравнение с `actualDuration` показывает выигрыш от мемоизации.

**Как понять, что нужна виртуализация?**
Тысячи элементов в DOM, заметные лаги при скролле/обновлении, большой размер DOM в Performance. Для сотен простых строк виртуализация обычно не нужна.

**Что делает `Suspense` при `lazy`?**
Показывает `fallback`, пока код компонента загружается. Так можно разбивать бандл по компонентам.

**`useMemo` везде — это оптимизация?**
Нет: это дополнительная работа и усложнение. Оптимизируют по результатам профилирования.

## Типичные ошибки

- Оптимизировать «по ощущениям», без Profiler и production-сборки.
- `memo`/`useMemo` везде без замеров.
- Рендерить тысячи узлов вместо виртуализации.
- Тяжёлые библиотеки в основном бандле, а не в `lazy`-чанках.
- `setState` на каждое `mousemove`/`scroll` без необходимости.
- Забывать про `key` (index) и компоненты внутри компонентов.
- Игнорировать сеть и размер бандла, оптимизируя только рендеры.
