> **Ответ за 30 секунд.** **Error Boundary** — компонент, который перехватывает ошибки, выброшенные **при рендере** его потомков (а также в методах жизненного цикла и эффектах), и показывает **запасной интерфейс** вместо падения всего приложения. Без границы необработанная ошибка рендера **размонтирует всё дерево** (белый экран). Граница пишется классом с `static getDerivedStateFromError` (обновить состояние → показать fallback) и `componentDidCatch` (логирование); функционального аналога в самом React нет, обычно берут библиотеку **`react-error-boundary`**. Граница **не ловит**: ошибки в **обработчиках событий**, в **асинхронном коде** (`setTimeout`, промисы), при серверном рендеринге и в самой границе. Такие ошибки обрабатывают `try/catch` или «пробрасывают» в границу (через `setState`, `useErrorBoundary().showBoundary`, либо внутри `startTransition`). Границы ставят **гранулярно** (на приложение, маршрут, независимые виджеты), чтобы падение одной части не ломало остальное.

- «Что произойдёт при ошибке в компоненте без границы?»

## Как это работает

```jsx
class ErrorBoundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {       // чистая функция: вернуть новое состояние
    return { error };
  }

  componentDidCatch(error, info) {               // побочные эффекты: логирование
    reportToService(error, info.componentStack);
  }

  reset = () => this.setState({ error: null });

  render() {
    if (this.state.error) return this.props.fallback({ error: this.state.error, reset: this.reset });
    return this.props.children;
  }
}
```

- `getDerivedStateFromError(error)` вызывается при ошибке в потомке; вернув состояние, вы заставляете границу отрендерить fallback.
- `componentDidCatch(error, info)` получает `info.componentStack` — цепочку компонентов, приведшую к ошибке (проверено: это строка). Здесь отправляют отчёт в Sentry и подобные сервисы.
- Границу нельзя написать на функциональном компоненте, потому что нужны именно эти методы класса. Поэтому используют класс или `react-error-boundary`:

```jsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
  fallbackRender={({ error, resetErrorBoundary }) => (
    <div role="alert">
      <p>Что-то пошло не так</p>
      <button onClick={resetErrorBoundary}>Повторить</button>
    </div>
  )}
  onError={(error, info) => report(error, info)}
  resetKeys={[userId]}
>
  <Profile id={userId} />
</ErrorBoundary>
```

`resetKeys` — при изменении любого значения граница, находящаяся в состоянии ошибки, сбрасывается и повторяет рендер (по документации библиотеки).

Проверено запуском (React 19): ошибка в потомке показывает fallback, а соседний компонент вне границы остаётся на месте (`fallback:boomsibling`).

## Что границы ловят и что нет

| Источник ошибки | Ловится границей? |
|---|---|
| Рендер компонента (в том числе дочерних) | **да** |
| Методы жизненного цикла, конструкторы | да |
| Ошибка в `useEffect` (проверено: `caught:effect-fail`) | да |
| Отклонённый промис в `use(promise)` внутри `Suspense` (проверено) | да |
| Ошибка из `startTransition` (в том числе в async-функции; проверено) | да |
| **Обработчики событий** (`onClick`) | **нет** (проверено: после клика с `throw` fallback не показан) |
| **Асинхронный код** (`setTimeout`, `fetch().then`, `async`/`await` вне переходов) | **нет** |
| Серверный рендеринг (SSR) | нет (там свои механизмы) |
| Ошибка в самой границе | нет (ловит граница выше) |

### Что делать с ошибками, которые граница не ловит

1. **`try/catch`** в обработчике/асинхронной функции, затем показать сообщение через состояние (например, `setError`).
2. **Проброс в границу** через `setState`, который бросает ошибку при рендере:

```jsx
function useThrowAsync() {
  const [, setState] = useState();
  return (error) => setState(() => { throw error; });   // ошибка выбрасывается во время рендера
}

const throwAsync = useThrowAsync();
fetch("/api").then(check).catch(throwAsync);
```

Проверено: ошибка из `Promise.reject(...).catch(throwAsync)` попала в границу (`caught:net`). В `react-error-boundary` для этого есть `useErrorBoundary().showBoundary(error)`.

3. **Выполнять асинхронную работу в `startTransition`** (React 19): ошибка, брошенная внутри (в том числе после `await`), попадает в ближайшую границу (проверено).

Выбор: ошибки ожидаемые (валидация, 404, «нет прав») показывайте на месте через состояние; непредвиденные (баги, сбой загрузки критичных данных) отправляйте в границу.

## Где ставить границы

- **Верхний уровень приложения** — последний рубеж: «Что-то пошло не так» + кнопка «Перезагрузить».
- **Маршруты/страницы** — ошибка на одной странице не ломает навигацию и шапку (в Next.js это файл `error.js` для сегмента маршрута).
- **Независимые виджеты** (чат, график, комментарии) — ошибка виджета не затрагивает остальное.
- **Вокруг ненадёжных частей**: сторонние компоненты, данные от пользователей, `lazy`-чанки (ошибка загрузки чанка тоже уходит в границу).

Чем мельче граница, тем выше устойчивость, но тем больше fallback-интерфейсов нужно продумать.

## Retry и сброс

```jsx
function Profile({ id }) {
  return (
    <ErrorBoundary resetKeys={[id]} fallbackRender={...}>
      <User id={id} />
    </ErrorBoundary>
  );
}
```

Свой сброс: метод `reset` (сбросить состояние `error`) и сравнение ключей в `componentDidUpdate`. Проверено: при `id: 1 → 2` (ошибка) показывается fallback, повторный рендер с тем же `id` ошибку не снимает, смена на `id = 3` — сбрасывает границу и показывает `user 3`. Если причина ошибки не устранена (сервер лежит), повторный рендер снова упадёт, поэтому «Повторить» нужно сочетать с повторным запросом данных (сброс кэша запросов, `queryClient.invalidateQueries`/`reset`).

## Логирование и мониторинг

- В `componentDidCatch`/`onError` отправляйте `error`, `componentStack`, версию приложения, пользователя (без чувствительных данных).
- В React 19 у `createRoot`/`hydrateRoot` есть опции **`onCaughtError`** (ошибка поймана границей), **`onUncaughtError`** (не поймана никем) и **`onRecoverableError`** (React автоматически восстановился, например, при несовпадении гидратации): удобно один раз настроить отправку отчётов на уровне корня (по документации React).
- Глобальные обработчики `window.onerror` и `unhandledrejection` ловят то, что не попало в границы (асинхронный код, обработчики событий).
- Инструменты: Sentry, Datadog RUM, LogRocket и аналоги — сборка source maps обязательна для читаемых стеков.
- В dev-режиме `componentDidCatch` в проверке вызвался **дважды** на одну ошибку (React повторяет рендер при ошибке); логирование делайте идемпотентным (в production не проверялось).

## Частые follow-up вопросы

**Почему границы — только классы?**
`getDerivedStateFromError` и `componentDidCatch` существуют только как методы класса, у хуков аналога нет.

**Ловит ли граница ошибки из `fetch` в `useEffect`?**
Нет, если ошибка возникает в асинхронном коде (`.then`, `await`). Ошибку нужно перехватить и либо показать через состояние, либо пробросить в границу.

**Что будет с состоянием компонентов под границей после ошибки?**
Поддерево, в котором произошла ошибка, заменяется fallback'ом и размонтируется (состояние теряется); после сброса оно создаётся заново.

**Чем границы ошибок отличаются от `try/catch`?**
`try/catch` работает для императивного кода, а рендер декларативен: нельзя обернуть JSX в `try/catch` и поймать ошибки дочерних компонентов — для этого и нужны границы.

**Как тестировать границы?**
Рендерить «бомбу» (компонент, который бросает ошибку), проверять fallback и сброс; подавлять шум `console.error`.

## Типичные ошибки

- Ожидать, что граница поймает ошибки из `onClick` или `fetch`.
- Одна граница на всё приложение: любая ошибка заменяет весь интерфейс.
- Граница без сброса: пользователь не может продолжить без перезагрузки страницы.
- Побочные эффекты в `getDerivedStateFromError` (их место — `componentDidCatch`).
- Показ технических деталей ошибки пользователю в production.
- Отсутствие логирования: ошибки видны только в консоли пользователя.
