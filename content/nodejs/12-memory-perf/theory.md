> **Ответ за 30 секунд.** Память JS-объектов живёт в **куче V8**, которой управляет сборщик мусора (GC). Куча делится на **young generation** (новые объекты, быстрая сборка *scavenge*) и **old generation** (выжившие объекты, *mark-sweep-compact*, частично параллельный и инкрементальный). Объект собирается, когда **недостижим** от корней (глобальные переменные, стек, замыкания). **Утечка** — это объект, который программа больше не использует, но на который ещё остаётся ссылка (неограниченный кэш, забытый слушатель, незакрытый таймер, глобальный массив). Диагностика: следим за `heapUsed`/`rss`, делаем **heap snapshot** (DevTools) в разные моменты и сравниваем. Производительность: **сначала измеряем** (CPU-профиль, event loop lag), затем оптимизируем горячие места; увеличение `--max-old-space-size` — не лечение утечки, а отсрочка.

## Устройство памяти

| Область | Что хранит |
|---|---|
| **Стек** | кадры вызовов, примитивы, ссылки; быстро выделяется/освобождается, ограничен (глубокая рекурсия ⇒ `RangeError: Maximum call stack size exceeded`) |
| **Куча V8** | объекты, массивы, строки, замыкания |
| **Вне кучи** | `Buffer`/`ArrayBuffer`, нативные аддоны, внутренние структуры Node |

`process.memoryUsage()`:

- `rss` — вся резидентная память процесса (куча, стек, код, буферы);
- `heapTotal` / `heapUsed` — выделенная/занятая куча V8;
- `external` — память нативных объектов, привязанных к JS (в т. ч. Buffer);
- `arrayBuffers` — память `ArrayBuffer`/`Buffer`.

Поэтому процесс может расти по `rss` из-за Buffer-ов, пока `heapUsed` стабилен.

## Сборка мусора

Основано на **гипотезе поколений**: большинство объектов живут недолго.

- **Young generation** (малая, единицы-десятки МБ): *scavenge* — копирующий сборщик, очень быстрый. Объекты, пережившие несколько сборок, **повышаются** в old.
- **Old generation**: **mark-sweep-compact**: помечаем достижимые объекты, удаляем остальные, уплотняем. Фазы выполняются инкрементально и параллельно (потоки GC), чтобы сокращать паузы *stop-the-world*.
- **Достижимость**: объект жив, если до него есть цепочка ссылок от корней. Циклические ссылки сами по себе не мешают сборке.

Лимит старой памяти задаётся `--max-old-space-size=<МБ>`; при превышении процесс падает с `FATAL ERROR: ... JavaScript heap out of memory`. Значение по умолчанию зависит от доступной памяти и версии; в контейнерах стоит задавать его осознанно, согласуя с лимитом контейнера.

## Типичные утечки

```js
// 1. Неограниченный кэш/глобальная коллекция
const cache = new Map();
app.get("/user/:id", async (req, res) => {
  if (!cache.has(req.params.id)) cache.set(req.params.id, await load(req.params.id)); // растёт вечно
});

// 2. Слушатели, которые не снимаются
app.get("/", (req, res) => bus.on("update", () => res.write("x")));

// 3. Таймеры и интервалы
setInterval(() => poll(bigObject), 1000);   // держит bigObject, пока интервал не очищен

// 4. Замыкания, удерживающие большие объекты
function handler(bigData) { return () => bigData.id; }   // bigData живёт, пока жив handler

// 5. Данные запроса, сохранённые в долгоживущем объекте
requestLog.push({ req, res });               // держит весь запрос
```

Также: промисы, которые никогда не разрешаются, накопление необработанных очередей, незакрытые соединения/стримы/дескрипторы, `console.log` огромных объектов в долгих процессах, неосвобождённые ресурсы в нативных аддонах.

Лечение: ограничить размер кэша (LRU/TTL), снимать слушатели, `clearInterval`, не хранить лишние ссылки, использовать `WeakMap`/`WeakRef` для метаданных, привязанных к объекту (не мешают его сборке).

## Как искать утечку

1. **Подтвердить**: график `heapUsed` после GC растёт со временем и не возвращается к базовому уровню (пила с растущим «дном»). Метрики (`process.memoryUsage()`, Prometheus, APM).
2. **Воспроизвести** нагрузкой и снять **heap snapshot**:
   - запуск `node --inspect server.js` и вкладка **Memory** в Chrome DevTools (`chrome://inspect`);
   - из кода: `v8.writeHeapSnapshot()`;
   - по сигналу: `node --heapsnapshot-signal=SIGUSR2 server.js`, затем `kill -USR2 <pid>`.
3. **Метод трёх снимков**: снимок А (после прогрева) → нагрузка → снимок B → нагрузка → снимок C. Сравниваем *Comparison* B↔C: объекты, которые прибавились в обоих интервалах, — подозреваемые.
4. В снимке смотрим **Retainers** (кто удерживает объект): путь до корня показывает, какая ссылка мешает сборке.
5. Исправить и повторить измерение.

Инструмент для сравнения нагрузки: `autocannon`; для общей диагностики: Clinic.js (`doctor`, `flame`, `heapprofiler`), `0x`.

## Производительность: измеряем, потом оптимизируем

**Не оптимизируйте вслепую.** Порядок:

1. **Метрики**: latency (p50/p95/p99), RPS, CPU, event loop lag (`monitorEventLoopDelay`), GC-паузы.
2. **Профиль CPU**: `node --cpu-prof app.js` создаёт `.cpuprofile` (открывается в Chrome DevTools → Performance/Memory или `speedscope`); флейм-граф показывает, где тратится время.
3. Определить, что именно: CPU (вычисления), I/O (БД, сеть), блокировка event loop или GC.

Типичные причины и решения:

| Симптом | Причина | Решение |
|---|---|---|
| Высокий CPU на одном ядре, большой lag | тяжёлый синхронный код, JSON больших объектов, регулярки | воркеры, потоковая обработка, оптимизация алгоритма |
| Долгие запросы, низкий CPU | ожидание I/O: медленная БД, последовательные `await` | параллелизм (`Promise.all`), индексы, кэш |
| N запросов в БД на 1 запрос API | **N+1** | `JOIN`, батчинг (`DataLoader`), `IN (...)` |
| Много соединений/рукопожатий | нет keep-alive и пула | пул соединений, переиспользование `http.Agent` |
| Большие ответы | нет сжатия/пагинации | `gzip/br`, пагинация, потоки |
| Повторяющиеся вычисления/запросы | нет кэша | in-memory LRU, Redis, HTTP-кэш, CDN |
| Долгие GC-паузы | огромная куча, много короткоживущих объектов | уменьшать аллокации, переиспользовать объекты, стримы |

Микрооптимизации V8 (однотипная форма объектов, отсутствие `delete`, монотонные массивы) обычно дают малый выигрыш против архитектурных: кэш, пулы, отказ от N+1, вынос тяжёлой работы.

## Частые follow-up вопросы

**`WeakMap` и `WeakRef` — зачем?**
`WeakMap` держит ключи-объекты «слабо»: если на ключ нет других ссылок, запись исчезнет вместе с ним. Подходит для кэшей метаданных. `WeakRef` — слабая ссылка на объект (может вернуть `undefined` после GC); применять осторожно, момент сборки недетерминирован.

**Можно ли вызвать GC вручную?**
Только с флагом `--expose-gc` (`global.gc()`); в продакшене не рекомендуется, пригодится для тестов и диагностики.

**Почему `rss` растёт, а `heapUsed` нет?**
Растут буферы/`external`, фрагментация или нативные аддоны.

**Утечка или просто кэш?**
Утечка — неограниченный рост. Кэш с лимитом/TTL выходит на плато.

**Как ведёт себя процесс при `heap out of memory`?**
Падает; оркестратор перезапустит, но корректной обработки нет. Лучше метрики и алерты заранее.

## Типичные ошибки

- Увеличивать `--max-old-space-size` вместо поиска утечки.
- Кэшировать без лимита и TTL.
- Подписываться на события в обработчике запроса и не отписываться.
- Оптимизировать без профиля.
- Измерять производительность на «горячем» одном запросе, а не под нагрузкой.
- Хранить в замыканиях `req`/`res` дольше, чем нужно.
