> **Ответ за 30 секунд.** Асинхронность в Node.js — это способ не блокировать главный поток во время ожидания I/O. Эволюция: **колбэки** (callback hell, error-first) → **промисы** (объект-результат будущего значения с состояниями *pending → fulfilled/rejected*, цепочки `.then`, единая обработка ошибок) → **async/await** (синтаксический сахар над промисами, код читается как синхронный). `await` не блокирует поток: он приостанавливает *функцию*, а продолжение ставится в очередь микрозадач. Независимые операции нужно запускать параллельно через `Promise.all`, а не `await` друг за другом.

## Что именно спрашивают

- «Что выведет код с `async/await` и `setTimeout`?» (порядок выполнения)
- «Как выполнить N запросов параллельно, но не больше 5 одновременно?»
- «Почему `await` внутри `forEach` не работает?»
- «Что будет с необработанным отклонённым промисом?»

## Колбэки и «ад колбэков»

Стиль Node.js ранних лет — **error-first callback**: первый аргумент — ошибка.

```js
fs.readFile("a.txt", "utf8", (err, data) => {
  if (err) return handle(err);
  fs.readFile("b.txt", "utf8", (err2, data2) => {
    if (err2) return handle(err2);
    // ...пирамида вложенности растёт
  });
});
```

Проблемы: вложенность, дублирование обработки ошибок, потеря контроля над потоком выполнения (колбэк может быть вызван дважды или ни разу), невозможность использовать `try/catch`.

## Промисы

**Promise** — объект, представляющий результат асинхронной операции. Состояния:

- **pending** — ожидание;
- **fulfilled** — выполнен со значением;
- **rejected** — отклонён с причиной.

Переход из pending в fulfilled/rejected происходит **один раз** и необратим (состояние *settled*).

```js
const p = new Promise((resolve, reject) => {
  setTimeout(() => resolve(42), 100);
});

p.then((v) => v + 1)           // каждый then возвращает НОВЫЙ промис
  .then((v) => console.log(v)) // 43
  .catch((e) => console.error(e))
  .finally(() => console.log("всегда"));
```

Ключевые свойства:

1. `.then(cb)` возвращает **новый** промис. Значение, возвращённое из `cb`, становится результатом; если вернули промис, цепочка «разворачивается» и ждёт его.
2. Исключение внутри `then` превращает возвращённый промис в *rejected*, ошибка «проваливается» вниз по цепочке до ближайшего `.catch`.
3. Колбэки `then` вызываются **асинхронно** (как микрозадачи), даже если промис уже выполнен.
4. Исключение, брошенное синхронно в executor `new Promise(...)`, тоже отклоняет промис.

### Промисификация колбэков

```js
import { promisify } from "node:util";
import fs from "node:fs";

const readFile = promisify(fs.readFile);
// чаще используют готовые промис-API:
import { readFile as readFileP } from "node:fs/promises";
```

## async/await

```js
async function load() {
  try {
    const user = await getUser(1);
    const posts = await getPosts(user.id);
    return { user, posts };
  } catch (err) {
    // ловит и синхронные ошибки, и отклонённые промисы
    throw new Error("load failed", { cause: err });
  }
}
```

- `async`-функция **всегда возвращает промис**. `return 5` ⇒ `Promise<5>`, `throw` ⇒ отклонённый промис.
- `await expr` приостанавливает выполнение *этой* функции до разрешения промиса. Главный поток при этом свободен.
- Продолжение после `await` — микрозадача, даже если значение не промис (`await 5`).
- Синхронная часть async-функции (до первого `await`) выполняется сразу, как в обычной функции.

### `return` против `return await`

```js
async function a() {
  try { return fetchData(); }        // ошибка НЕ будет поймана этим catch
  catch (e) { /* не сработает */ }
}
async function b() {
  try { return await fetchData(); }  // ошибка поймана
  catch (e) { /* сработает */ }
}
```

Внутри `try/catch` нужен `return await`, иначе промис «убегает» наружу до того, как ошибка может быть перехвачена.

## Последовательно или параллельно

Самая частая ошибка: ожидание независимых операций по очереди.

```js
// Последовательно: время = t1 + t2 + t3
const a = await fetchA();
const b = await fetchB();
const c = await fetchC();

// Параллельно: время = max(t1, t2, t3)
const [a2, b2, c2] = await Promise.all([fetchA(), fetchB(), fetchC()]);
```

Последовательность нужна только когда следующий шаг **зависит** от результата предыдущего.

## Комбинаторы

| Метод | Результат | Когда отклоняется |
|---|---|---|
| `Promise.all([...])` | массив значений (в исходном порядке) | при первой же ошибке (**fail-fast**) |
| `Promise.allSettled([...])` | массив `{status, value\|reason}` | **никогда** |
| `Promise.race([...])` | результат первого *завершившегося* (успех или ошибка) | если первый завершившийся отклонён |
| `Promise.any([...])` | результат первого **успешного** | если отклонены все (`AggregateError`) |

Важно: `Promise.all` при ошибке **не отменяет** остальные операции. Они продолжают выполняться, просто их результат игнорируется. Для реальной отмены нужен `AbortController`.

```js
const results = await Promise.allSettled(urls.map((u) => fetch(u)));
const ok = results.filter((r) => r.status === "fulfilled").map((r) => r.value);
```

## Ограничение конкурентности

`Promise.all` на 10 000 URL откроет 10 000 соединений сразу. Нужно ограничить число одновременных задач (пул/семафор): готовые решения — `p-limit`, `p-queue`; суть алгоритма — N «воркеров», каждый берёт следующую задачу из общей очереди, когда освободился (см. задание в практике).

## Отмена и таймауты

```js
const res = await fetch(url, { signal: AbortSignal.timeout(3000) });
```

`AbortController`/`AbortSignal` — стандартный способ отмены в `fetch`, `fs/promises`, `events.once`, `timers/promises` и др. `AbortSignal.timeout(ms)` создаёт сигнал, который сработает по таймауту.

## Необработанные ошибки

Если промис отклонён и нигде нет обработчика, возникает событие `unhandledRejection`. **Начиная с Node.js 15 режим по умолчанию — `throw`**: без обработчика `unhandledRejection` это превращается в `uncaughtException` и процесс завершается с кодом 1. Ловить в `process.on("unhandledRejection")` для «продолжения как ни в чём не бывало» нельзя — только залогировать и корректно завершиться (см. тему про ошибки и graceful shutdown).

## Ловушки

**1. `await` в `forEach` не ждёт.**

```js
items.forEach(async (item) => {
  await save(item);   // forEach не знает о промисах
});
console.log("готово"); // выполнится ДО сохранения

// Правильно:
await Promise.all(items.map((item) => save(item)));      // параллельно
for (const item of items) await save(item);              // последовательно
```

**2. Забытый `await`.** Функция вернёт промис вместо значения, а ошибка потеряется как unhandled rejection.

**3. Неожиданный `async` в executor.** `new Promise(async (resolve) => ...)` — антипаттерн: ошибки внутри не отклонят промис.

**4. Смешивание колбэков и промисов** — вызов `resolve` дважды или не вызов вообще оставляет промис вечно в pending.

**5. «Fire and forget»** без `.catch`: ошибка станет unhandled rejection и уронит процесс.

## Частые follow-up вопросы

**Что выведет код?**

```js
console.log(1);
setTimeout(() => console.log(2), 0);
(async () => {
  console.log(3);
  await null;
  console.log(4);
})();
Promise.resolve().then(() => console.log(5));
console.log(6);
```

Вывод: `1 3 6 4 5 2`. Синхронно: 1, 3 (до первого `await`), 6. Потом микрозадачи в порядке постановки: продолжение async-функции (4), затем `.then` (5). Потом таймер (2).

**Можно ли отменить промис?** Сам промис нет. Отменяют *операцию* через `AbortSignal`, а результат игнорируют.

**Чем `Promise.race` с таймаутом хуже `AbortSignal.timeout`?** `race` лишь перестаёт ждать, операция (запрос, соединение) продолжает работать и тратить ресурсы.

**Что такое thenable?** Любой объект с методом `then`; `await` и `Promise.resolve` умеют его «разворачивать».

**`Promise.withResolvers()`** (Node 22+) возвращает `{ promise, resolve, reject }` — удобно, когда нужно разрешить промис снаружи.
