> **Ответ за 30 секунд.** **HTTP** — текстовый протокол запрос–ответ поверх TCP (и QUIC в HTTP/3), **stateless**: каждый запрос самодостаточен. **REST** — стиль проектирования API вокруг **ресурсов** (`/users/42`), где действие задаёт HTTP-метод (`GET` читает, `POST` создаёт, `PUT` заменяет, `PATCH` частично меняет, `DELETE` удаляет), а результат — статус-код (2xx успех, 4xx ошибка клиента, 5xx ошибка сервера). Безопасные (`GET`, `HEAD`) и идемпотентные (`GET`, `PUT`, `DELETE`) методы определяют, что можно безопасно повторять. В Node.js REST строят на `node:http` или фреймворках (Express, Fastify), где обработка запроса — **цепочка middleware**: функции `(req, res, next)`, каждая либо отвечает, либо вызывает `next()`.

- «`401` или `403`? `400` или `422`? Когда `409`?»

- «Express против Fastify: что выбрать и почему?»
- «Как кэшировать на уровне HTTP?» (`Cache-Control`, `ETag`)

## Методы HTTP

| Метод | Назначение | Безопасный | Идемпотентный | Тело |
|---|---|---|---|---|
| `GET` | прочитать ресурс | да | да | нет |
| `HEAD` | то же без тела | да | да | нет |
| `POST` | создать / выполнить действие | нет | **нет** | да |
| `PUT` | **заменить** ресурс целиком | нет | да | да |
| `PATCH` | **частично** изменить | нет | зависит от реализации | да |
| `DELETE` | удалить | нет | да | обычно нет |
| `OPTIONS` | узнать возможности (CORS preflight) | да | да | нет |

- **Безопасный** — не меняет состояние сервера.
- **Идемпотентный** — N одинаковых запросов дают то же состояние, что и один. Поэтому повторять `PUT`/`DELETE` при сетевой ошибке безопасно, а `POST` — нет (получите дубликат заказа).
- Для идемпотентности `POST` используют **Idempotency-Key**: клиент шлёт уникальный ключ, сервер сохраняет результат и на повторе отдаёт его же.

## Статус-коды

| Код | Значение | Когда |
|---|---|---|
| `200 OK` | успех | чтение, обновление с телом |
| `201 Created` | создано | `POST`; заголовок `Location` на новый ресурс |
| `204 No Content` | успех без тела | `DELETE`, `PUT` без ответа |
| `301/302/307/308` | редиректы | `307/308` сохраняют метод |
| `304 Not Modified` | кэш актуален | условный запрос (`If-None-Match`) |
| `400 Bad Request` | синтаксически неверный запрос | битый JSON |
| `401 Unauthorized` | **не аутентифицирован** (нет/неверные учётные данные) | нет токена |
| `403 Forbidden` | аутентифицирован, но **нет прав** | чужой ресурс |
| `404 Not Found` | ресурса нет | неверный id или URL; иногда намеренно вместо `403`, чтобы не раскрывать существование чужого ресурса |
| `405 Method Not Allowed` | метод не поддерживается | `DELETE /users`, если коллекция не умеет удаляться; добавьте заголовок `Allow` |
| `409 Conflict` | конфликт состояния | дубликат уникального поля, версия устарела |
| `422 Unprocessable Content` | синтаксис верен, **семантика** нет | ошибки валидации |
| `429 Too Many Requests` | превышен лимит | rate limit, заголовок `Retry-After` |
| `500 Internal Server Error` | баг на сервере | необработанное исключение; детали — только в логи |
| `502/503/504` | шлюз/недоступен/таймаут | апстрим упал (502), перегрузка или деплой (503), апстрим не ответил вовремя (504) |

Частая путаница: `401` — «кто вы?», `403` — «я знаю, кто вы, но вам нельзя».

## Принципы REST

1. **Ресурсы и URL-существительные**: `/orders/17/items`, а не `/getOrderItems`.
2. **Методы определяют действие**, а не URL.
3. **Stateless**: сервер не хранит контекст клиента между запросами (токен/идентификатор приходит в каждом запросе).
4. **Единообразный интерфейс**: предсказуемые URL, форматы, коды.
5. **Кэшируемость**: ответы размечаются заголовками кэша.
6. Представления: чаще JSON; согласование через `Accept`/`Content-Type`.

Практики: множественное число для коллекций, вложенность не глубже 2 уровней, версионирование (`/v1/…` или заголовок), единый формат ошибок, фильтры/сортировка/пагинация в query-параметрах, `PATCH` для частичных изменений.

```
GET    /users            список (с пагинацией)
POST   /users            создать → 201 + Location: /users/42
GET    /users/42         получить
PUT    /users/42         заменить целиком
PATCH  /users/42         изменить поля
DELETE /users/42         удалить → 204
GET    /users/42/orders  заказы пользователя
```

## Пагинация

- **Offset/limit** (`?limit=20&offset=40`): просто, но при вставках/удалениях элементы «прыгают» или дублируются, а `OFFSET` в БД на больших смещениях медленный (сканирует пропускаемые строки).
- **Cursor/keyset** (`?limit=20&after=<курсор>`): курсор — значение последней записи (например, `id`/`createdAt`). Стабильно и быстро (`WHERE id > $cursor ORDER BY id LIMIT 20`), но нет «перейти на страницу N».

## Кэширование

- `Cache-Control: max-age=3600, public` / `private` / `no-store`.
- **ETag** + `If-None-Match`: сервер отвечает `304`, если ресурс не изменился (экономит трафик).
- `Last-Modified` + `If-Modified-Since`.
- `Vary` — по каким заголовкам различается кэш (например, `Accept-Encoding`).

## Middleware

Middleware — функции в цепочке, имеющие доступ к `req`, `res` и `next`.

```js
import express from "express";
const app = express();

app.use(express.json());                      // 1: парсит JSON-тело
app.use((req, res, next) => {                 // 2: логирование
  const t = Date.now();
  res.on("finish", () => console.log(req.method, req.url, res.statusCode, Date.now() - t, "ms"));
  next();                                     // передаём управление дальше
});
app.get("/users/:id", auth, getUser);         // 3: маршрут + route-level middleware
app.use((req, res) => res.status(404).json({ error: "not found" }));  // 4: «ничего не подошло»
app.use((err, req, res, next) => { /* 5: error handler — 4 аргумента */ });
```

Правила:

- **Порядок регистрации = порядок выполнения.** Парсер тела должен идти раньше маршрутов, error handler — последним.
- Middleware должно либо **завершить ответ**, либо вызвать `next()`; иначе запрос «зависнет».
- `next(err)` пропускает обычные middleware и ведёт в error handler.
- Типичные задачи: логирование, аутентификация, валидация, rate limit, CORS, сжатие, `helmet` (заголовки безопасности).

### Как это устроено (compose)

```js
function compose(middlewares) {
  return (req, res) => {
    let i = -1;
    const dispatch = (idx) => {
      if (idx <= i) throw new Error("next() called multiple times");
      i = idx;
      const fn = middlewares[idx];
      if (!fn) return;
      return fn(req, res, () => dispatch(idx + 1));
    };
    return dispatch(0);
  };
}
```

## Express и Fastify

| | Express | Fastify |
|---|---|---|
| Идея | минимальный, огромная экосистема | быстрый, схемы, плагины |
| Валидация | сторонние (zod, joi) | **JSON Schema** встроена (и сериализация ответа) |
| async-ошибки | Express 5 — автоматически; в 4 вручную | из коробки |
| Расширение | `app.use` | плагины с инкапсуляцией (`register`, декораторы) |
| Производительность | достаточная | выше (быстрая маршрутизация и сериализация) |
| Типизация | через `@types` | встроенная поддержка TypeScript |

Выбор: Express — привычность и экосистема; Fastify — производительность и строгие контракты. NestJS — надстройка над ними для крупных приложений.

## Валидация

Никогда не доверяйте входу: валидируйте тело, query, params (zod/joi/JSON Schema). Возвращайте `400/422` с описанием полей. Вытаскивайте из тела только ожидаемые поля (защита от **mass assignment**).

## HTTP/1.1, HTTP/2, HTTP/3

- **HTTP/1.1**: keep-alive, но head-of-line blocking на соединении (браузеры открывают ~6 соединений).
- **HTTP/2**: мультиплексирование запросов в одном TCP-соединении, сжатие заголовков (HPACK).
- **HTTP/3**: поверх QUIC (UDP), без блокировки на уровне транспорта, быстрее при потерях.
- Для Node обычно TLS и HTTP/2/3 терминирует reverse proxy (nginx, Cloudflare, ingress).

## Частые follow-up вопросы

**Чем `PUT` отличается от `PATCH`?**
`PUT` заменяет ресурс целиком (отсутствующие поля сбрасываются), идемпотентен. `PATCH` меняет только присланные поля.

**Что вернуть при создании ресурса?**
`201 Created`, заголовок `Location` и (опционально) тело с созданным ресурсом.

**Что такое идемпотентность и как сделать идемпотентным `POST`?**
Повтор не меняет результат. Делают через `Idempotency-Key` или бизнес-ключ с уникальным ограничением в БД.

**Что такое preflight-запрос?**
`OPTIONS` перед «непростым» кросс-доменным запросом: браузер спрашивает разрешение (CORS).

**Почему нельзя отправлять тело в GET?**
Спецификация не запрещает, но семантики нет; кэши, прокси и серверы могут его игнорировать.

**Что произойдёт, если middleware не вызвало `next()` и не ответило?**
Запрос будет висеть до таймаута.

## Типичные ошибки

- Всегда возвращать `200`, а ошибку класть в тело.
- Глаголы в URL (`/createUser`).
- Путаница `401` и `403`.
- Парсер тела после маршрутов.
- Отсутствие валидации входа и лимита размера тела.
- `OFFSET`-пагинация на больших таблицах.
- Двойной ответ: `res.send` и затем `next()` или повторный `send` («Cannot set headers after they are sent»).
