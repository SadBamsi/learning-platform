## 1. Что такое Node.js

**Node.js** — это среда выполнения (runtime) для JavaScript вне браузера. Важно понимать три вещи:

- Node.js — **не язык**. Язык — JavaScript (стандарт ECMAScript).
- Node.js — **не фреймворк**. Это платформа, на которой фреймворки (Express, Fastify, NestJS) работают.
- Node.js — **программа**, которая умеет читать `.js`-файл, исполнять его и давать коду доступ к возможностям операционной системы: файлам, сети, процессам, таймерам.

### 1.1. Немного истории

До 2009 года JavaScript жил только в браузере. Сервера писали на PHP, Java, Python, Ruby. Райан Дал (Ryan Dahl) заметил проблему: традиционные серверы (например, Apache) создавали **отдельный поток на каждое соединение**. Пока поток ждёт ответа от диска или базы, он простаивает, но память занимает. При тысячах одновременных соединений это становится дорого.

Идея Дала: взять быстрый движок V8 из Chrome и построить вокруг него **асинхронный неблокирующий ввод-вывод** в одном потоке. Так в 2009 году появился Node.js. Позже (2010) появился npm, а экосистема пакетов сделала Node.js массовым инструментом.

С 2015 года проектом управляет OpenJS Foundation. Выходят версии: чётные (20, 22, 24…) становятся **LTS** (Long Term Support, долгая поддержка), нечётные — короткоживущие. Для обучения и продакшена бери активную LTS-версию.

### 1.2. Из чего состоит Node.js

Node.js — это связка нескольких компонентов:

| Компонент | Что делает |
|---|---|
| **V8** | Движок JavaScript от Google. Компилирует JS в машинный код (JIT-компиляция) и исполняет его. |
| **libuv** | Библиотека на C. Реализует event loop, асинхронную работу с файлами, сетью, DNS, таймерами; содержит пул потоков. |
| **Core-модули (стандартная библиотека)** | `fs`, `path`, `http`, `https`, `os`, `crypto`, `events`, `stream`, `zlib`, `child_process`, `worker_threads` и т. д. Часть написана на JS, часть на C++. |
| **Привязки (bindings) на C++** | «Мост» между JS-кодом и C/C++ библиотеками (OpenSSL, zlib, libuv, HTTP-парсер). |
| **npm** | Менеджер пакетов, поставляется вместе с Node.js. |

Схема того, как твой код достигает системы:

```
Твой JS-код
   │
   ▼
Core-модули (fs, http, ...)
   │
   ▼
C++ bindings
   │
   ├──► V8  (исполняет JS)
   └──► libuv (event loop, пул потоков, системные вызовы ОС)
```

### 1.3. JavaScript в браузере и в Node.js

Язык один и тот же, но окружение разное.

| | Браузер | Node.js |
|---|---|---|
| Глобальный объект | `window` | `globalThis` (также `global`) |
| DOM, `document`, `localStorage` | есть | **нет** |
| Файловая система | нет (только через специальные API) | есть (`fs`) |
| Создание HTTP-сервера | нет | есть (`http`) |
| Модули | ES Modules | CommonJS и ES Modules |
| Переменные окружения | нет | `process.env` |

Многие веб-API, к которым ты привык, в современных версиях Node.js тоже есть: `fetch`, `URL`, `AbortController`, `setTimeout`, `TextEncoder`, `structuredClone`, `console`.

## 2. Модель выполнения: один поток и event loop

### 2.1. Проблема, которую решает асинхронность

Представь кафе с одним официантом. Есть два подхода:

1. **Блокирующий.** Официант принял заказ, пошёл на кухню, *стоит и ждёт*, пока блюдо приготовят, несёт его, и только потом идёт к следующему гостю.
2. **Неблокирующий.** Официант принял заказ, передал на кухню и сразу идёт к следующему столику. Когда кухня готова, она звонит, и официант разносит блюдо.

Node.js работает по второму принципу. «Официант» — это **главный поток**, в котором выполняется твой JavaScript. «Кухня» — операционная система и пул потоков libuv, которые делают медленную работу (чтение диска, сеть).

Ключевое следствие: **пока главный поток занят вычислением, он не может обработать ничего другого**. Если ты запустишь в нём тяжёлый цикл на 5 секунд, весь сервер будет «заморожен» на 5 секунд для всех пользователей.

### 2.2. Что такое event loop

**Event loop (цикл событий)** — это механизм в libuv, который по кругу проверяет: «Есть ли готовые события, чьи callback-функции пора выполнить?». Алгоритм упрощённо такой:

1. Запускается твой скрипт, выполняется синхронный код сверху вниз (это и есть выполнение в *call stack*).
2. Все асинхронные операции (таймеры, чтение файла, сетевой запрос) передаются системе, а их callback-функции ждут.
3. Когда стек пуст, event loop начинает крутиться: берёт готовые callback'и и выполняет их по очереди.
4. Если больше нечего ждать (нет таймеров, открытых сокетов и т. п.), процесс завершается.

Именно поэтому простой скрипт `console.log("hi")` завершается сразу, а скрипт с запущенным HTTP-сервером живёт бесконечно: открытый сокет держит цикл «живым».

### 2.3. Фазы event loop

Каждый проход цикла называется *tick* (итерация) и проходит через фазы в фиксированном порядке:

```
   ┌───────────────────────────┐
┌─►│           timers          │  setTimeout / setInterval
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │     pending callbacks     │  отложенные системные callback'и
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │       idle, prepare       │  внутреннее использование
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │           poll            │  новые события I/O (файлы, сеть)
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │           check           │  setImmediate
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
└──┤      close callbacks      │  socket.on("close", ...)
   └───────────────────────────┘
```

- **timers** — выполняет callback'и `setTimeout` и `setInterval`, срок которых наступил. Важно: задержка — это *минимум*, а не гарантия. `setTimeout(fn, 100)` значит «не раньше чем через 100 мс».
- **poll** — главная фаза: получает новые события ввода-вывода и выполняет их callback'и. Если очередь пуста, цикл может подождать здесь прихода событий (но не дольше, чем до ближайшего таймера).
- **check** — выполняет callback'и `setImmediate`.
- **close callbacks** — обработчики закрытия (`socket.destroy()` и т. п.).

### 2.4. Микрозадачи: `process.nextTick` и промисы

Между фазами (точнее, после каждого callback'а) Node.js опустошает две особые очереди:

1. **`process.nextTick`** — самая приоритетная очередь.
2. **Микрозадачи промисов** (`.then`, `await`, `queueMicrotask`).

Порядок: сначала *вся* очередь `nextTick`, потом *вся* очередь промисов, потом идём дальше по циклу.

Разбор примера:

```js
console.log("1: синхронный код");

setTimeout(() => console.log("2: setTimeout"), 0);
setImmediate(() => console.log("3: setImmediate"));
Promise.resolve().then(() => console.log("4: promise"));
process.nextTick(() => console.log("5: nextTick"));

console.log("6: синхронный код");
```

Вывод:

```
1: синхронный код
6: синхронный код
5: nextTick
4: promise
2: setTimeout        (или после 3 — см. ниже)
3: setImmediate
```

Почему так:
1. Сначала выполняется весь синхронный код — строки 1 и 6.
2. Затем опустошается `nextTick`-очередь — 5.
3. Затем очередь промисов — 4.
4. Затем начинается event loop: фаза timers → 2, фаза check → 3.

Порядок `setTimeout(…, 0)` и `setImmediate` **в основном модуле не гарантирован**: он зависит от скорости запуска процесса. Но *внутри* callback'а ввода-вывода `setImmediate` всегда сработает раньше, потому что сразу за фазой poll идёт check.

> ⚠️ Опасность: если `process.nextTick` будет рекурсивно вызывать сам себя, очередь никогда не опустеет, и event loop **не сможет перейти к следующей фазе** — ввод-вывод «зголодает». Для отложенных действий чаще используй `setImmediate` или промисы.

### 2.5. Пул потоков (thread pool)

Раз JS однопоточный, кто делает настоящую работу? Здесь два механизма:

1. **Асинхронные системные вызовы ОС** — для сети (TCP, UDP, HTTP) ядро ОС само уведомляет о готовности данных (epoll на Linux, kqueue на macOS, IOCP на Windows). Потоки не нужны.
2. **Пул потоков libuv** — для операций, которые ОС не умеет делать асинхронно: работа с файловой системой, DNS-запросы `dns.lookup`, часть `crypto` (например, `pbkdf2`, `scrypt`), `zlib`. По умолчанию в пуле **4 потока**. Размер можно изменить переменной окружения `UV_THREADPOOL_SIZE` (до 1024).

Итог: **твой JS-код однопоточный, но Node.js как процесс использует несколько потоков внутри**. Ты не пишешь потоки сам, и поэтому не сталкиваешься с классическими проблемами многопоточности (гонки данных, взаимные блокировки) в своём коде.

### 2.6. Блокирующий и неблокирующий код

```js
const fs = require("node:fs");

// БЛОКИРУЮЩИЙ вариант: поток стоит, пока файл читается
console.log("до");
const data = fs.readFileSync("big.txt", "utf8");
console.log("после, длина:", data.length);

// НЕБЛОКИРУЮЩИЙ вариант: чтение уходит в систему, поток свободен
console.log("до");
fs.readFile("big.txt", "utf8", (err, data) => {
  if (err) throw err;
  console.log("файл прочитан, длина:", data.length);
});
console.log("после (выведется РАНЬШЕ, чем 'файл прочитан')");
```

Правила:

- В **скриптах и CLI-утилитах** блокирующие `*Sync`-функции допустимы: там всё равно не нужно обслуживать параллельных клиентов, а код проще.
- В **серверах** используй асинхронные варианты. Один `readFileSync` в обработчике запроса блокирует *всех* остальных клиентов на время чтения.
- Исключение: `*Sync`-вызовы при **старте** приложения (чтение конфигурации) обычно приемлемы.

### 2.7. CPU-bound и I/O-bound задачи

- **I/O-bound** (упираются в ввод-вывод): запросы к БД, чтение файлов, HTTP-запросы. Node.js справляется с ними отлично.
- **CPU-bound** (упираются в процессор): обработка изображений, сжатие, сложные вычисления, парсинг огромного JSON. Они **блокируют event loop**.

Что делать с CPU-bound задачами:
- вынести в **`worker_threads`** (настоящие дополнительные JS-потоки внутри одного процесса);
- запустить отдельный процесс через `child_process`;
- использовать кластер (`cluster`) для использования всех ядер процессора;
- отдать задачу специализированному сервису или написать нативное расширение.

Пример проблемы:

```js
const http = require("node:http");

http
  .createServer((req, res) => {
    if (req.url === "/block") {
      const end = Date.now() + 5000;
      while (Date.now() < end) {} // 5 секунд «жжём» CPU
      res.end("done");
    } else {
      res.end("fast");
    }
  })
  .listen(3000);
```

Пока выполняется запрос `/block`, даже мгновенный `/` не получит ответа — сервер «залип». Попробуй сам в практической части.

## 3. Первые шаги с Node.js

### 3.1. Запуск кода

```bash
node --version          # версия Node.js
node app.js             # выполнить файл
node                    # запустить REPL (интерактивная консоль)
node -e "console.log(1+1)"   # выполнить строку кода
node --watch app.js     # перезапускать при изменении файла (Node 18.11+)
```

**REPL** (Read-Eval-Print Loop) удобен для быстрых экспериментов: вводишь выражение и сразу видишь результат. Выход — `Ctrl+C` дважды или `.exit`.

### 3.2. Глобальные объекты

В Node.js без `import` доступны:

- `console` — вывод (`log`, `error`, `warn`, `table`, `time`/`timeEnd`);
- `process` — информация о текущем процессе и управление им;
- `setTimeout`, `setInterval`, `setImmediate` и их `clear*`-пары;
- `queueMicrotask`, `structuredClone`, `fetch`, `URL`, `URLSearchParams`, `AbortController`, `TextEncoder`/`TextDecoder`;
- `Buffer` — работа с бинарными данными;
- `globalThis` — глобальный объект.

В CommonJS-модулях дополнительно есть `require`, `module`, `exports`, `__dirname`, `__filename` (подробно — в следующем уроке).

### 3.3. Объект `process`

`process` — один из самых полезных объектов:

```js
console.log(process.version);        // например, v22.11.0
console.log(process.platform);       // 'win32', 'linux', 'darwin'
console.log(process.cwd());          // текущая рабочая директория
console.log(process.pid);            // идентификатор процесса
console.log(process.argv);           // аргументы командной строки
console.log(process.env.HOME);       // переменные окружения
console.log(process.memoryUsage());  // использование памяти
console.log(process.uptime());       // сколько секунд работает процесс
```

**Аргументы командной строки.** `process.argv` — массив: нулевой элемент — путь к `node`, первый — путь к скрипту, дальше — твои аргументы.

```js
// node greet.js Олег
const name = process.argv[2];
console.log(`Привет, ${name ?? "незнакомец"}!`);
```

**Коды выхода.** Процесс завершается с кодом: `0` — успех, любое другое число — ошибка. Это важно для скриптов и CI.

```js
if (!process.argv[2]) {
  console.error("Нужно передать имя");
  process.exit(1);
}
```

**События процесса:**

```js
process.on("exit", (code) => console.log("Выход с кодом", code));
process.on("SIGINT", () => {          // Ctrl+C
  console.log("Останавливаюсь...");
  process.exit(0);
});
process.on("uncaughtException", (err) => {
  console.error("Необработанная ошибка:", err);
  process.exit(1);
});
```

### 3.4. Вывод в консоль: больше, чем `log`

```js
console.log("обычный вывод");          // stdout
console.error("ошибка");               // stderr
console.table([{ a: 1, b: 2 }, { a: 3, b: 4 }]);

console.time("loop");
for (let i = 0; i < 1e6; i++) {}
console.timeEnd("loop");               // loop: 3.2ms
```

`stdout` и `stderr` — разные потоки. Это позволяет, например, перенаправить результаты в файл (`node app.js > out.txt`), а ошибки по-прежнему видеть на экране.

## 4. Когда использовать Node.js, а когда нет

**Хорошо подходит:**
- REST и GraphQL API, бэкенд для сайтов и мобильных приложений;
- приложения реального времени: чаты, уведомления, WebSocket;
- стриминг данных и прокси;
- инструменты разработчика: сборщики (Vite, webpack), линтеры, CLI-утилиты;
- серверный рендеринг (Next.js — тот самый, на котором построена эта платформа);
- скрипты автоматизации.

**Подходит хуже:**
- тяжёлые вычисления, видео- и аудиокодирование, научные расчёты в основном потоке;
- системы, где критична предсказуемая латентность до микросекунд.

**Преимущества:** один язык на клиенте и сервере, огромная экосистема npm, высокая производительность на I/O, быстрый старт разработки.

**Недостатки:** нужно следить за блокировкой event loop; качество пакетов в npm неоднородно; «ад колбэков» (в современном коде решается `async/await`).

## 5. Частые ошибки новичков

1. **Ожидание синхронного результата от асинхронной функции.**
   ```js
   let text;
   fs.readFile("a.txt", "utf8", (err, data) => { text = data; });
   console.log(text); // undefined — колбэк ещё не выполнился!
   ```
2. **Блокировка event loop** тяжёлым циклом или `*Sync` в обработчике запроса.
3. **Игнорирование ошибок** в колбэках: первый аргумент `err` нужно всегда проверять.
4. **Путаница с `this` и `window`**: в Node.js `window` не существует, используй `globalThis`.
5. **Запуск из неправильной папки**: относительные пути (`"./a.txt"`) считаются от `process.cwd()`, а не от расположения скрипта.

## 6. Краткое резюме урока

- Node.js = V8 + libuv + core-модули + npm.
- Твой JS-код выполняется в **одном потоке**; медленные операции делегируются ОС и пулу потоков.
- **Event loop** по кругу проходит фазы: timers → poll → check → close; между ними выполняются микрозадачи (`nextTick`, затем промисы).
- Блокирующий код в сервере вредит всем клиентам; тяжёлые вычисления выноси в `worker_threads`.
- `process` — доступ к аргументам, окружению, сигналам и коду выхода.
