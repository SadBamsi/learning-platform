> **Ответ за 30 секунд.** Event loop — бесконечный цикл libuv, который берёт готовые колбэки из очередей и выполняет их в главном потоке. Цикл идёт по **фазам**: *timers* → *pending callbacks* → *idle/prepare* → *poll* (I/O) → *check* (`setImmediate`) → *close callbacks*. Между колбэками движок опустошает **микрозадачи**: сначала очередь `process.nextTick`, затем очередь промисов (`.then`, `await`, `queueMicrotask`). Поэтому порядок такой: синхронный код → `nextTick` → промисы → фазы цикла.

## Что именно спрашивают

Классика: *«Что выведет этот код?»* с `setTimeout`, `setImmediate`, `Promise.then`, `process.nextTick` и `console.log`. Плюс вопросы: «в каких фазах выполняется что», «чем `nextTick` отличается от `setImmediate`», «как можно заблокировать event loop», «что такое starvation».

## Модель в одной картинке

```
   ┌───────────────────────────┐
┌─►│          timers           │  setTimeout / setInterval
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │     pending callbacks     │  отложенные системные колбэки (напр. часть ошибок TCP)
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │       idle, prepare       │  внутреннее
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │           poll            │  ждём/обрабатываем I/O: сокеты, файлы
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
│  │           check           │  setImmediate
│  └─────────────┬─────────────┘
│  ┌─────────────▼─────────────┐
└──┤      close callbacks      │  socket.on('close')
   └───────────────────────────┘

  После КАЖДОГО колбэка:  очередь nextTick → очередь микрозадач (промисы)
```

Ключевые правила:

1. Каждая фаза имеет свою FIFO-очередь колбэков. Фаза выполняет колбэки, пока очередь не опустеет или не достигнут лимит, затем цикл переходит к следующей.
2. **Poll** — единственная фаза, где цикл может «спать», ожидая I/O. Если есть запланированные `setImmediate`, он не спит, а идёт в *check*. Если ближайший таймер уже подошёл, цикл возвращается к *timers*.
3. Таймер `setTimeout(fn, 0)` — это «не раньше чем через ~1 мс», а не «сразу». Точное время зависит от загруженности цикла.
4. После каждого колбэка (начиная с Node 11, как и в браузере) выполняются `nextTick`-очередь и очередь микрозадач.

## Микрозадачи: nextTick против промисов

- **`process.nextTick(fn)`** — отдельная очередь, имеет приоритет над промисами. Опустошается полностью до начала обработки микрозадач промисов.
- **Промисы** (`.then`, `.catch`, `await`) и **`queueMicrotask`** — очередь микрозадач V8.
- Если из микрозадачи добавляется новая микрозадача, она тоже выполняется **до** возврата к циклу. Поэтому бесконечная рекурсия через `nextTick` или промисы «морит голодом» (**starvation**) таймеры и I/O: цикл не доходит до следующей фазы.

Документация Node.js помечает `process.nextTick` как Legacy и рекомендует `queueMicrotask()`.

### Разбор классической задачи

```js
console.log("1 sync");
setTimeout(() => console.log("2 timeout"), 0);
setImmediate(() => console.log("3 immediate"));
Promise.resolve().then(() => console.log("4 promise"));
process.nextTick(() => console.log("5 nextTick"));
console.log("6 sync end");
```

Вывод в CommonJS:

```
1 sync
6 sync end
5 nextTick
4 promise
2 timeout    ← 2 и 3 могут поменяться местами (см. ниже)
3 immediate
```

Логика: сначала весь синхронный код → очередь `nextTick` → очередь промисов → фазы цикла.

**Нюанс для ESM (частый «вопрос со звёздочкой»):** в ES-модуле сам код модуля исполняется внутри промис-цепочки, поэтому `Promise.then` срабатывает **раньше** `process.nextTick`: порядок будет `sync → promise → nextTick`. Это я проверил запуском на Node 24; в CommonJS — наоборот.

### `setTimeout(0)` против `setImmediate`

- **В главном модуле** порядок **не гарантирован**: зависит от того, успел ли пройти 1 мс до входа в цикл. Запустите несколько раз — увидите оба варианта.
- **Внутри I/O-колбэка** (`fs.readFile(..., () => { ... })`) `setImmediate` **всегда** выполнится первым: после фазы *poll* идёт *check*, а таймеры — только на следующем витке.

```js
import fs from "node:fs";
fs.readFile(import.meta.filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate")); // всегда первым
});
```

### Вложенные микрозадачи

```js
Promise.resolve().then(() => {
  console.log("p1");
  process.nextTick(() => console.log("tick внутри промиса"));
  Promise.resolve().then(() => console.log("p2 (вложенный)"));
});
process.nextTick(() => {
  console.log("t1");
  Promise.resolve().then(() => console.log("промис внутри tick"));
  process.nextTick(() => console.log("t2 (вложенный)"));
});
```

Вывод в CommonJS: `t1`, `t2 (вложенный)`, `p1`, `промис внутри tick`, `p2 (вложенный)`, `tick внутри промиса`.
Разбор: очередь `nextTick` опустошается целиком (вместе с вложенным `t2`), затем очередь промисов опустошается целиком (включая вложенные), и только после этого снова проверяется `nextTick`.

## Как заблокировать event loop

Любая синхронная операция, которая выполняется долго:

- тяжёлые циклы, `JSON.parse`/`JSON.stringify` огромных объектов;
- `*Sync`-методы (`readFileSync`, `pbkdf2Sync`, `execSync`);
- **ReDoS** — регулярное выражение с катастрофическим бэктрекингом на пользовательском вводе;
- сортировка/агрегация больших массивов в памяти.

Как лечить:

1. **Разбить работу на чанки** и отдавать управление циклу: `await setImmediate()` из `node:timers/promises` между порциями.
2. **Вынести в `worker_threads`** или отдельный процесс/сервис.
3. **Стримить** данные вместо загрузки целиком.
4. **Мониторить**: `perf_hooks.monitorEventLoopDelay()` показывает задержку цикла (event loop lag); рост lag — сигнал блокировок.

```js
import { setImmediate as tick } from "node:timers/promises";

async function sumBig(n) {
  let sum = 0;
  for (let i = 0; i < n; i++) {
    sum += i;
    if (i % 1_000_000 === 0) await tick(); // пустить в цикл другие события
  }
  return sum;
}
```

## Частые follow-up вопросы

**Чем `setImmediate` отличается от `process.nextTick`?**
Название вводит в заблуждение. `nextTick` выполняется *сразу после текущей операции*, до перехода к следующей фазе; `setImmediate` — в фазе *check* текущего витка цикла, после I/O.

**Что такое starvation и как её получить?**
Рекурсивный `process.nextTick` (или бесконечная цепочка промисов) никогда не отдаёт управление циклу — таймеры и I/O не выполняются. Рекурсивный `setImmediate` такой проблемы не создаёт: каждый вызов откладывается на следующий виток.

**Выполняется ли `await` синхронно?**
Нет. Код после `await` — это продолжение в виде микрозадачи, даже если промис уже выполнен.

**Гарантирует ли `setTimeout(fn, 100)` вызов ровно через 100 мс?**
Нет, только «не раньше». Если цикл занят, колбэк запоздает.

**Где живёт `setInterval` и в чём его подвох?**
В фазе *timers*. Если колбэк длится дольше интервала, вызовы не накладываются друг на друга (Node не запускает их параллельно), но «дрейфуют»; для периодических задач с асинхронным телом безопаснее рекурсивный `setTimeout`.

## Типичные ошибки

- Утверждать, что порядок `setTimeout(0)` и `setImmediate` всегда фиксирован.
- Путать очередь `nextTick` и очередь промисов: у `nextTick` приоритет выше (в CommonJS).
- Рекурсивно вызывать `nextTick` для «разбиения» тяжёлой работы: это не отдаёт управление циклу. Нужен `setImmediate`.
- Считать, что `async` функция «не блокирует»: синхронная часть до первого `await` выполняется в главном потоке как обычно.
