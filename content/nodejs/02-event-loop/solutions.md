## Решения

### Задание 1

**CommonJS:**

```
A
F
H
E        ← nextTick
D        ← промис
G        ← продолжение после await null
B / C    ← порядок B и C в главном модуле не гарантирован
```

**ESM:** синхронная часть та же (`A F H`), но затем промисы идут раньше `nextTick`: `D`, `G`, `E`, затем `B`/`C`.

Почему: `await null` ставит продолжение (`G`) в очередь микрозадач; она идёт после `D`, потому что `D` был поставлен раньше. В ESM код модуля исполняется внутри промис-цепочки, поэтому очередь промисов опустошается раньше очереди `nextTick`.

### Задание 2

Первым всегда выведется `tick` (микрозадача сразу после колбэка), затем **`immediate`**, затем `timeout`. Порядок гарантирован: колбэк `readFile` выполняется в фазе *poll*, следующая фаза — *check* (`setImmediate`), а таймеры будут проверены только на следующем витке.

### Задание 3

Каждый `process.nextTick(work)` добавляет в очередь `nextTick` новый колбэк, а очередь опустошается **до** возврата в event loop. Цикл не доходит до фазы *timers*, пока рекурсия не завершится (starvation). Таймер сработает только после 1 млн вызовов.

Исправление — `setImmediate` (откладывает на следующий виток цикла). Чтобы не терять в производительности, обрабатываем пачку элементов за один колбэк:

```js
setTimeout(() => console.log("timer fired"), 10);

let n = 0;
const TOTAL = 1e8;
function work() {
  for (let i = 0; i < 100_000 && n < TOTAL; i++) n++; // пачка
  if (n < TOTAL) setImmediate(work); // отдаём управление циклу
  else console.log("work finished", n);
}
work();
```

Теперь `timer fired` выведется **до** `work finished`: между пачками цикл успевает проверить таймеры. (Если оставить `1e6`, работа закончится быстрее 10 мс и разницы не будет видно: увеличьте `TOTAL`.)

### Задание 4

```js
import { monitorEventLoopDelay } from "node:perf_hooks";

const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();

setInterval(() => {
  // значения в наносекундах
  console.log(
    `lag mean=${(h.mean / 1e6).toFixed(1)} мс, max=${(h.max / 1e6).toFixed(1)} мс`
  );
  h.reset();
}, 1000);

// эмуляция блокировки через 3 секунды
setTimeout(() => {
  const end = Date.now() + 500;
  while (Date.now() < end) {}
}, 3000);
```

Значения `mean`/`min`/`max` в гистограмме приходят в наносекундах и **включают период опроса** (`resolution`), поэтому «фон» около 10 мс — норма. Смотрите на `max`: после блокировки он вырастет примерно до 500 мс. В продакшене такую метрику экспортируют в мониторинг и ставят алерт.

### Задание 5

```js
import { setImmediate as tick } from "node:timers/promises";

async function heavy() {
  let s = 0;
  for (let i = 0; i < 5e8; i++) {
    s += i;
    if (i % 5e6 === 0) await tick(); // отдаём управление циклу
  }
  return s;
}

const timer = setInterval(() => console.log("tick"), 100);
console.log(await heavy());
clearInterval(timer);
```

Вывод `tick` идёт параллельно с вычислением. Цена: общее время немного выросло из-за переключений. Для действительно тяжёлых вычислений правильнее `worker_threads`.

### Задание 6

Пример ответа:

«Event loop — цикл libuv, который по кругу проходит фазы: timers (просроченные `setTimeout`/`setInterval`), pending callbacks, poll (получение событий ввода-вывода от ОС и выполнение их колбэков; здесь цикл может ждать, если делать нечего), check (`setImmediate`) и close callbacks. У каждой фазы своя FIFO-очередь колбэков. После каждого колбэка Node опустошает очередь `process.nextTick`, затем очередь микрозадач — промисы и `queueMicrotask`. Поэтому порядок: синхронный код, `nextTick`, промисы, затем фазы цикла. Если очередей пусто и таймеров нет, а активных ресурсов тоже, процесс завершается».
