> **Ответ за 30 секунд.** Тесты строят по **пирамиде**: много быстрых **unit-тестов** (одна функция/модуль, зависимости заменены), меньше **integration-тестов** (несколько модулей, реальная БД/HTTP), ещё меньше медленных **e2e-тестов** (весь продукт глазами пользователя). Хороший тест — **быстрый, изолированный, детерминированный и проверяет поведение, а не реализацию**. Внешние зависимости (время, случайность, сеть, БД) заменяют **тестовыми дублёрами** (stub, spy, mock, fake) или контролируют через внедрение зависимостей. В Node.js есть встроенный раннер **`node:test`** (`node --test`) с `assert`, моками и таймерами; популярны также **Jest** и **Vitest**.

## Что именно спрашивают

- «Какие бывают виды тестов? Что такое пирамида тестирования?»
- «Чем stub отличается от mock и spy?»
- «Как тестировать код, зависящий от времени, сети, БД?»
- «Как протестировать HTTP-эндпоинт?»
- «Что такое flaky-тест и как с ними бороться?»
- «Достаточно ли 100% покрытия?»

## Виды тестов

| Вид | Что проверяет | Скорость | Хрупкость | Количество |
|---|---|---|---|---|
| **Unit** | функцию/класс изолированно | мс | низкая | много |
| **Integration** | взаимодействие модулей, БД, HTTP-слой | сотни мс — секунды | средняя | умеренно |
| **E2E** | весь сценарий через UI/API (Playwright, Cypress) | секунды — минуты | высокая | мало |
| **Contract** | согласованность формата между сервисами | быстро | низкая | по границам сервисов |

**Пирамида**: основание — unit, середина — integration, вершина — e2e. «Перевёрнутая пирамида» (в основном e2e) — медленно, дорого и нестабильно. Для фронтенда иногда используют «трофей» тестирования, где больше integration-тестов.

## Структура теста: AAA

```js
import { test } from "node:test";
import assert from "node:assert/strict";

test("applyDiscount: скидка 10% для заказа от 1000", () => {
  // Arrange: подготовка
  const order = { total: 1200 };
  // Act: действие
  const result = applyDiscount(order);
  // Assert: проверка
  assert.equal(result.total, 1080);
});
```

Хорошие привычки: одно поведение — один тест; понятные имена («что, при каких условиях, ожидаемо»); тесты независимы и не зависят от порядка; проверяем **публичное поведение**, а не внутренние детали.

## node:test

```js
import { describe, it, before, after, mock } from "node:test";
import assert from "node:assert/strict";

describe("UserService", () => {
  it("возвращает пользователя", async () => {
    const repo = { findById: mock.fn(async (id) => ({ id, name: "Ann" })) };
    const svc = new UserService(repo);

    const user = await svc.get(7);

    assert.deepEqual(user, { id: 7, name: "Ann" });
    assert.equal(repo.findById.mock.callCount(), 1);
    assert.deepEqual(repo.findById.mock.calls[0].arguments, [7]);
  });

  it("бросает NotFoundError", async () => {
    const svc = new UserService({ findById: async () => null });
    await assert.rejects(() => svc.get(1), { name: "NotFoundError" });
  });
});
```

Запуск: `node --test` (находит `*.test.js`, `*.spec.js`, файлы в `test/`), `node --test --watch`, флаги для покрытия (`--experimental-test-coverage` в ряде версий). Есть `before/after/beforeEach/afterEach`, `test.skip`, `test.todo`, `mock.method`, `mock.timers`.

## Тестовые дублёры

| Тип | Назначение |
|---|---|
| **Dummy** | заглушка-параметр, который не используется |
| **Stub** | возвращает заранее заданные ответы |
| **Spy** | «шпион»: запоминает вызовы (аргументы, число), поведение не меняет |
| **Mock** | stub + проверка ожиданий о вызовах |
| **Fake** | упрощённая рабочая реализация (in-memory репозиторий) |

В повседневной речи «mock» часто означает любой дублёр. Важно понимать суть: **что подменяется и что проверяется** — состояние (результат) или взаимодействие (вызовы).

Чрезмерные моки приводят к тестам, которые проверяют реализацию и ломаются при рефакторинге. Для границ системы (БД, сеть, время) моки уместны; внутреннюю логику лучше проверять на реальных объектах.

## Внедрение зависимостей

Чтобы код тестировался, зависимости передают снаружи, а не создают внутри:

```js
// Плохо: жёсткая зависимость
async function getWeather(city) {
  const r = await fetch(`https://api.example.com/w?c=${city}`);
  return r.json();
}

// Хорошо: зависимость внедряется
function makeWeatherService({ fetchFn = fetch, now = Date.now } = {}) {
  return { async get(city) { const r = await fetchFn(`https://api.example.com/w?c=${city}`); return r.json(); } };
}
```

## Время, случайность, сеть

- **Время**: `mock.timers.enable({ apis: ["setTimeout", "Date"] })` и `tick(ms)` — тест не ждёт реально.
- **Случайность**: внедрять генератор или фиксировать seed.
- **Сеть**: не ходить в реальный интернет (медленно и нестабильно); подменять `fetch`, использовать локальный сервер или перехват (`undici MockAgent`, `nock`, MSW).
- **Файловая система**: временные каталоги (`fs.mkdtemp`), очистка в `after`.

```js
import { test, mock } from "node:test";
test("debounce вызывает функцию один раз", (t) => {
  t.mock.timers.enable({ apis: ["setTimeout"] });
  const fn = mock.fn();
  const d = debounce(fn, 100);
  d(); d(); d();
  t.mock.timers.tick(100);
  assert.equal(fn.mock.callCount(), 1);
});
```

## Тестирование HTTP-API

Поднимаем сервер на **случайном свободном порту** и ходим настоящим HTTP-клиентом:

```js
import { before, after, test } from "node:test";
import http from "node:http";

let server, base;
before(async () => {
  server = http.createServer(app);
  await new Promise((r) => server.listen(0, r));           // порт 0 = выбрать свободный
  base = `http://localhost:${server.address().port}`;
});
after(() => server.close());

test("GET /health", async () => {
  const res = await fetch(`${base}/health`);
  assert.equal(res.status, 200);
  assert.deepEqual(await res.json(), { ok: true });
});
```

(Для Express/Fastify также используют `supertest` или `app.inject()` у Fastify, который не открывает порт.)

## Тесты с базой данных

- **Реальная БД в контейнере** (Docker/Testcontainers) — максимально близко к продакшену; нужно сбрасывать состояние между тестами.
- **Транзакция на тест + rollback** — быстро изолирует данные.
- **Отдельная схема/БД на воркер**, миграции перед запуском.
- SQLite/in-memory вместо PostgreSQL — быстро, но ведёт себя по-другому (типы, индексы, блокировки), поэтому багов в продакшене не ловит.

## Flaky-тесты

Тест, который то проходит, то падает без изменений кода. Причины: реальное время и `sleep`, зависимость от порядка тестов, общее состояние (БД, глобальные переменные), гонки, сеть, случайные данные, ограниченные ресурсы CI. Лечение: детерминировать время/случайность, изолировать данные, не использовать `setTimeout` для ожидания (ждать событие/условие), завершать ресурсы (серверы, таймеры), запускать тесты независимо и в случайном порядке.

## Покрытие кода

Покрытие показывает, **какие строки выполнялись**, а не что они **проверены**. 100% покрытия не гарантирует отсутствие багов (тест может выполнять код и ничего не проверять). Разумная цель — покрытие критичной логики и граничных случаев; ориентироваться на значимость тестов (в том числе **mutation testing**), а не на цифру.

## Инструменты

| Инструмент | Особенности |
|---|---|
| `node:test` | встроенный, без зависимостей, моки, таймеры, покрытие |
| **Jest** | популярный, снапшоты, моки, встроенный раннер; тяжелее |
| **Vitest** | совместим с API Jest, быстрый, нативная поддержка ESM/TS (Vite) |

## TDD

Цикл **Red → Green → Refactor**: сначала падающий тест, затем минимальный код, затем рефакторинг. Помогает проектировать тестируемый код; не догма: применяют там, где требования ясны.

## Частые follow-up вопросы

**Что тестировать в первую очередь?**
Бизнес-логику, граничные случаи, обработку ошибок, критичные сценарии (оплата, права доступа), регрессии найденных багов.

**Нужно ли тестировать приватные методы?**
Нет, проверяется публичное поведение; приватные детали можно менять без поломки тестов.

**Чем snapshot-тесты опасны?**
Их легко «обновить не глядя»; большие снапшоты никто не читает, и регрессии пропускаются.

**Как ускорить тесты в CI?**
Параллельный запуск, ограничение e2e, кэширование зависимостей, быстрые unit-тесты первыми, шардирование.

**Почему тест, использующий `setTimeout(…, 1000)` для ожидания — плохой?**
Он медленный и нестабильный: либо ждёт зря, либо не успевает. Нужны mock timers или ожидание конкретного события.

## Типичные ошибки

- Тесты зависят друг от друга и от порядка.
- Реальные сеть/время/случайность в unit-тестах.
- Один огромный тест на всё.
- Проверка деталей реализации (вызов приватных функций, порядок внутренних вызовов).
- Серверы и таймеры не закрываются: процесс тестов «висит».
- Игнорирование падающих flaky-тестов вместо исправления.
