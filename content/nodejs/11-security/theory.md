> **Ответ за 30 секунд.** Главный принцип безопасности веб-приложения — **не доверять никаким входным данным** (тело, query, заголовки, cookie, файлы, ответы чужих API) и применять защиту в несколько слоёв. Базовый набор: **параметризованные запросы** (против SQL-инъекций), **экранирование вывода + CSP** (против XSS), **`SameSite`-cookie и CSRF-токены** (против CSRF), **явный allow-list в CORS**, **валидация входа по схеме**, **rate limiting**, **секреты вне кода**, **обновление зависимостей**, **заголовки безопасности** (`helmet`), **минимальные привилегии**. Важно понимать, что **CORS — это ограничение браузера, а не защита сервера**: `curl` его игнорирует.

## Инъекции

**SQL-инъекция** — пользовательский ввод становится частью SQL-кода.

```js
// Уязвимо: email = "' OR '1'='1" — отдаст всех пользователей
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// Безопасно: параметры передаются отдельно от текста запроса
db.query("SELECT * FROM users WHERE email = $1", [email]);
```

Экранирование вручную ненадёжно. Параметризованные запросы/ORM — основной способ. Имена таблиц и колонок (`ORDER BY ${col}`) нельзя параметризовать: используйте allow-list допустимых значений.

**NoSQL-инъекция** (MongoDB): если тело `{"email": "a@b.c", "password": {"$ne": null}}` попадёт прямо в запрос, условие «пароль не null» выполнится для любого пользователя. Защита: проверять типы (строка, а не объект), валидировать схемой, санитизировать операторы.

**Command injection** — см. тему про масштабирование: `execFile` вместо `exec`, без shell.

## XSS (Cross-Site Scripting)

Злоумышленник внедряет JS на страницу, и он выполняется в браузере жертвы **с правами вашего сайта** (кража токена, действия от имени пользователя).

Виды: **stored** (скрипт сохранён в БД, например, в комментарии), **reflected** (в параметре URL, отражается в ответе), **DOM-based** (небезопасная работа с DOM на клиенте: `innerHTML`, `document.write`).

Защита:

- **Экранирование при выводе** в нужном контексте (HTML, атрибут, JS, URL). Шаблонизаторы и React экранируют текст по умолчанию.
- Не использовать `innerHTML`/`dangerouslySetInnerHTML` с непроверенными данными; при необходимости — санитайзер (DOMPurify).
- **CSP** (`Content-Security-Policy`): запрещает inline-скрипты и загрузку с неразрешённых источников — эффективный второй рубеж.
- `HttpOnly` cookie: даже при XSS скрипт не прочитает токен сессии.
- Валидация и нормализация на входе.

## CSRF (Cross-Site Request Forgery)

Чужая страница заставляет браузер жертвы отправить запрос на ваш сайт, **автоматически приложив cookie** авторизации.

Защита:

- **`SameSite=Lax/Strict`** у cookie (в современных браузерах `Lax` — по умолчанию);
- **CSRF-токен** (случайное значение, проверяемое сервером; double-submit cookie / synchronizer token);
- проверка заголовков **`Origin`/`Referer`**;
- изменяющие операции — не через `GET`;
- API с токеном в заголовке `Authorization` (не cookie) к CSRF не уязвим, но тогда важнее защита от XSS.

**XSS vs CSRF:** XSS исполняет чужой код **на вашем сайте**; CSRF отправляет запрос **с чужого сайта** от имени пользователя. XSS обходит защиту от CSRF (скрипт может прочитать токен), поэтому XSS опаснее.

## CORS

**Same-Origin Policy** запрещает странице одного origin (схема + хост + порт) читать ответы другого. **CORS** — механизм, с помощью которого сервер **разрешает** браузеру такие обращения через заголовки `Access-Control-*`.

```
Origin: https://app.example.com           ← браузер добавляет сам
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true    ← если нужны cookie
```

- **Простые запросы** (GET/POST с простыми заголовками и типами) отправляются сразу; браузер решает, показать ли ответ странице.
- **Непростые** (методы `PUT/PATCH/DELETE`, `Content-Type: application/json`, свои заголовки) предваряет **preflight** — `OPTIONS` с `Access-Control-Request-Method/Headers`; сервер отвечает `Access-Control-Allow-Methods/Headers`, `Access-Control-Max-Age`.
- `Allow-Origin: *` нельзя сочетать с `credentials`. Для запросов с cookie origin должен быть конкретным.
- **Не отражайте слепо заголовок `Origin`** в `Allow-Origin` вместе с `credentials: true`: это эквивалентно «разрешено всем». Используйте allow-list.
- CORS **не защищает сервер**: запрос всё равно доходит и выполняется (особенно «простой»), сервер просто не даёт странице прочитать ответ. Прямые HTTP-клиенты (`curl`, Postman) CORS не применяют.

## Path traversal

```js
// Уязвимо: /files/..%2F..%2Fetc%2Fpasswd
res.sendFile(path.join(PUBLIC_DIR, req.params.name));

// Безопасно: нормализуем и проверяем, что путь остался внутри каталога
const full = path.resolve(PUBLIC_DIR, req.params.name);
if (!full.startsWith(PUBLIC_DIR + path.sep)) return res.status(403).end();
```

Лучше: брать файл по идентификатору из БД, а не по пути от пользователя.

## SSRF (Server-Side Request Forgery)

Сервер делает запрос по URL, который задал пользователь (превью ссылок, вебхуки, импорт по URL). Злоумышленник указывает внутренние адреса: `http://localhost:6379`, `http://169.254.169.254/` (метаданные облака) и получает доступ к внутренним сервисам. Защита: allow-list доменов, запрет приватных и loopback-диапазонов **после DNS-резолва** (защита от DNS rebinding), отключение редиректов, таймауты, изоляция сети.

## Prototype pollution

Небезопасное слияние объектов позволяет «отравить» `Object.prototype` и повлиять на всё приложение:

```js
function merge(target, src) {
  for (const k in src) {
    if (typeof src[k] === "object") merge((target[k] ??= {}), src[k]);
    else target[k] = src[k];
  }
}
merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
({}).isAdmin; // true — у всех объектов!
```

Защита: игнорировать ключи `__proto__`, `constructor`, `prototype`; использовать `Object.create(null)` или `Map`; валидировать по схеме; обновлять зависимости (lodash и подобные имели такие уязвимости); `Object.freeze(Object.prototype)` в крайнем случае; флаг `--disable-proto=delete`.

## ReDoS

Регулярное выражение с катастрофическим бэктрекингом (`/^(a+)+$/`) на специально подобранной строке выполняется экспоненциальное время и блокирует event loop.

```js
/^(a+)+$/.test("a".repeat(30) + "!");   // секунды и больше → весь сервер «висит»
```

Защита: избегать вложенных квантификаторов и перекрывающихся альтернатив, ограничивать длину входа, использовать движки с линейным временем (RE2), проверять регулярки линтерами (`safe-regex`).

## Rate limiting и защита от перебора

- Лимит запросов по IP/пользователю/ключу (`429` + `Retry-After`): библиотеки `express-rate-limit`, `@fastify/rate-limit`, на уровне шлюза/CDN.
- Алгоритмы: fixed window, sliding window, **token bucket** (допускает всплески), leaky bucket.
- Усиленные лимиты для `/login`, `/reset-password`, дорогих эндпоинтов.
- Ограничения размера тела и числа параметров, таймауты запросов (защита от Slowloris).
- В кластере счётчики хранят в общем хранилище (Redis).

## Общие практики

- **Валидация входа** по схеме (zod, JSON Schema); белые списки полей (защита от **mass assignment**).
- **`helmet`**: заголовки `Content-Security-Policy`, `X-Content-Type-Options`, `Strict-Transport-Security` (HSTS), `X-Frame-Options`/`frame-ancestors` и др.
- **HTTPS везде**, HSTS, `Secure`-cookie.
- **Секреты** — в переменных окружения/секрет-менеджере (Vault, cloud KMS), не в репозитории; ротация; `.env` в `.gitignore`; не логировать токены и пароли.
- **Зависимости**: `npm audit`, lock-файл, Dependabot/Renovate, минимизация числа пакетов (подробнее — в теме про npm).
- **Ошибки**: клиенту — безопасное сообщение, стек — только в логи.
- **Принцип наименьших привилегий**: пользователь БД с минимальными правами, контейнер не от root.
- **Логирование и аудит** значимых событий (входы, смена прав), мониторинг аномалий.
- Не использовать `eval`, `new Function`, `vm` с недоверенным кодом.

## Частые follow-up вопросы

**Защищает ли CORS от CSRF?**
Нет. «Простой» кросс-сайтовый `POST` (форма) уходит на сервер независимо от CORS. От CSRF защищают `SameSite`, токены и проверка `Origin`.

**Как сервер отвечает на preflight?**
`204/200` с `Access-Control-Allow-Origin`, `-Methods`, `-Headers` (и, при необходимости, `-Credentials`, `-Max-Age`). Preflight не должен требовать авторизации.

**Чем хешировать токены сброса пароля?**
Генерировать криптостойким `randomBytes`, хранить хеш (SHA-256 подходит, так как токен длинный и случайный), ограничить срок и сделать одноразовым.

**Можно ли доверять заголовку `X-Forwarded-For`?**
Только если он установлен вашим доверенным прокси. Иначе клиент подделает его и обойдёт rate limit по IP.

**Что такое clickjacking?**
Встраивание вашей страницы в невидимый iframe для обманных кликов. Защита: `Content-Security-Policy: frame-ancestors 'none'` или `X-Frame-Options`.

## Типичные ошибки

- Конкатенация строк в SQL.
- `Access-Control-Allow-Origin: *` вместе с авторизацией по cookie или отражение любого `Origin`.
- Хранение секретов в репозитории.
- Проверка прав только на фронтенде.
- Отдача подробных ошибок (стек, SQL) клиенту.
- Устаревшие зависимости с известными CVE.
- Доверие к данным «изнутри» (из своей БД, от другого сервиса) без валидации.
