> **Ответ за 30 секунд.** Node.js — это среда выполнения JavaScript вне браузера: движок **V8** исполняет JS, библиотека **libuv** даёт event loop и асинхронный ввод-вывод, а встроенные модули (`fs`, `http`, `crypto`…) открывают доступ к ОС. Ваш JS-код выполняется в **одном потоке**, но ввод-вывод не блокирует его: сеть обслуживает ядро ОС (epoll/kqueue/IOCP), а файлы, DNS, криптографию и сжатие — пул потоков libuv. Поэтому Node хорош для I/O-bound задач (API, прокси, WebSocket) и плох для тяжёлых вычислений на главном потоке.

## Что именно спрашивают

Вопрос почти всегда звучит так: *«Node.js однопоточный? Как он тогда обслуживает много клиентов?»* Это проверка, понимаете ли вы разницу между **потоком, исполняющим JS** и **процессом Node.js**. Ответ «да, однопоточный» — неполный и считается ошибкой уровня junior.

## Из чего состоит Node.js

| Компонент | Роль |
|---|---|
| **V8** | Движок JS от Google: парсит, JIT-компилирует в машинный код, управляет памятью и сборкой мусора. |
| **libuv** | Кроссплатформенная C-библиотека: event loop, асинхронный I/O, таймеры, пул потоков. |
| **Core-модули** | `fs`, `http`, `net`, `crypto`, `stream`, `zlib`, `worker_threads`… — часть на JS, часть на C++. |
| **C++ bindings** | «Мост» между JS и C/C++ библиотеками (OpenSSL, zlib, HTTP-парсер, libuv). |

Node.js — **не язык** (язык — JavaScript) и **не фреймворк** (Express, Fastify, NestJS работают поверх него).

## Что значит «однопоточный»

В процессе Node.js на самом деле несколько потоков:

1. **Главный поток** — в нём выполняется ваш JS и крутится event loop. Одновременно исполняется **только один** кусок вашего кода.
2. **Пул потоков libuv** — по умолчанию **4** потока (меняется через `UV_THREADPOOL_SIZE`). Выполняет «блокирующие по природе» операции: большинство операций `fs`, `dns.lookup`, `crypto.pbkdf2`/`scrypt`/`randomBytes`, асинхронный `zlib`.
3. **Служебные потоки V8** — сборка мусора, компиляция.
4. **Worker threads** — если вы сами их создали (см. тему про масштабирование).

**Сеть в пул не попадает.** Сокеты неблокирующие, а ядро ОС само сообщает libuv, когда на сокете есть данные (`epoll` на Linux, `kqueue` на macOS/BSD, `IOCP` на Windows). Один поток может следить за десятками тысяч сокетов.

```
 JS-код ──► V8 ──► вызов fs.readFile / http / crypto
                         │
                         ▼
                   libuv (event loop)
              ┌──────────┴───────────┐
        сеть: epoll/kqueue/IOCP    пул потоков (4)
        (без потоков)              fs, dns.lookup, crypto, zlib
              └──────────┬───────────┘
                         ▼
          результат ставится в очередь → колбэк в главном потоке
```

## Почему это эффективно

Классическая модель «поток на соединение» (Apache, старые Java-серверы) тратит память (стек потока ≈ мегабайты) и время на переключение контекста, хотя большую часть времени поток **ждёт** диск или БД. Node.js не ждёт: он регистрирует колбэк и идёт обрабатывать следующее событие. Когда операция завершилась, колбэк возвращается в главный поток.

Цена: **любая долгая синхронная операция в главном потоке блокирует всех клиентов**.

```js
// Плохо: пока считается цикл, сервер не ответит НИКОМУ
app.get("/report", (req, res) => {
  let sum = 0;
  for (let i = 0; i < 5e9; i++) sum += i;
  res.json({ sum });
});
```

## Когда Node.js подходит, а когда нет

| Подходит (I/O-bound) | Не подходит «из коробки» (CPU-bound) |
|---|---|
| REST/GraphQL API, BFF | Кодирование видео, обработка изображений на лету |
| WebSocket, чаты, стриминг | Тяжёлая математика, ML-инференс |
| Прокси, API-шлюзы | Большие синхронные парсинги/агрегации |
| CLI-инструменты, SSR | Любой CPU-bound код без вынесения в worker/сервис |

CPU-bound задачи не «запрещены»: их выносят в `worker_threads`, отдельный процесс или другой сервис (на Go/Rust/Python).

## Node.js против браузера

- Нет `window`, `document`, DOM; глобальный объект — `globalThis` (в Node это ещё и `global`).
- Есть `process`, `Buffer`, `__dirname` (в CommonJS), доступ к файловой системе и сети без ограничений песочницы.
- `fetch`, `AbortController`, `URL`, `structuredClone`, `TextEncoder` доступны глобально в современных версиях (`fetch` — начиная с Node 18).
- Один и тот же язык, но разное окружение: код, зависящий от `window`, на сервере упадёт (типичная ошибка в SSR).

## Версии и LTS

Чётные мажорные версии становятся **LTS** (долгая поддержка) и подходят для продакшена; нечётные живут недолго. На собеседовании полезно сказать: «в продакшене использую активную LTS, фиксирую версию в `.nvmrc` или `engines` и в Docker-образе».

## Частые follow-up вопросы

**Что будет, если в обработчике запроса выполнить `while(true)`?**
Event loop остановится: сервер перестанет принимать новые запросы и отвечать на текущие, таймеры не сработают, health-check упадёт. Единственный выход — убить процесс.

**Читает ли `fs.readFile` файл в главном потоке?**
Нет. Вызов уходит в пул потоков libuv, а колбэк/промис возвращается в главный поток после завершения. А вот `fs.readFileSync` блокирует главный поток.

**Почему `crypto.pbkdf2` с 8 параллельными вызовами выполнится «двумя волнами»?**
Потому что в пуле 4 потока: первые 4 задачи выполняются параллельно, остальные ждут в очереди.

**Как использовать все ядра CPU?**
Запускать несколько процессов (`cluster`, PM2, контейнеры за балансировщиком) или выносить вычисления в `worker_threads`. Подробнее — в теме «Масштабирование».

**Node.js быстрее Java/Go?**
Некорректный вопрос. Для I/O-bound нагрузки Node масштабируется хорошо, для CPU-bound — заметно уступает. Правильный ответ называет тип нагрузки, а не «быстрее/медленнее вообще».

## Типичные ошибки

- Говорить «Node.js однопоточный» без уточнений про libuv и пул.
- Считать, что `async/await` делает код многопоточным. Нет: это синтаксис над промисами, JS-код по-прежнему исполняется в одном потоке.
- Использовать `*Sync`-методы (`readFileSync`, `pbkdf2Sync`) в обработчиках запросов. Допустимо при старте приложения.
- Забывать, что у пула потоков ограниченный размер: много параллельных `fs`/`crypto`-операций могут «задушить» друг друга и даже DNS.
