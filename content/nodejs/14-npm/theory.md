> **Ответ за 30 секунд.** **npm** — менеджер пакетов Node.js и публичный реестр пакетов. Манифест проекта — **`package.json`**: имя, версия, скрипты, зависимости (`dependencies` — нужны в рантайме, `devDependencies` — только для разработки и сборки, `peerDependencies` — «ожидаю, что эту библиотеку установит потребитель»). Версии подчиняются **semver** (`MAJOR.MINOR.PATCH`); диапазоны `^1.2.3` (до следующего major) и `~1.2.3` (до следующего minor) дают гибкость, а **lock-файл** (`package-lock.json`) фиксирует точные версии всего дерева для воспроизводимых сборок. В CI используют **`npm ci`** (строго по lock-файлу), локально — `npm install`. Главные риски — **supply chain**: уязвимые и вредоносные зависимости; их снижают lock-файлом, `npm audit`, ревью обновлений, ограничением скриптов установки и минимумом пакетов.

## package.json

```json
{
  "name": "my-service",
  "version": "1.4.2",
  "private": true,
  "type": "module",
  "main": "./dist/index.js",
  "exports": { ".": { "import": "./dist/index.js", "require": "./dist/index.cjs" } },
  "bin": { "my-cli": "./bin/cli.js" },
  "scripts": {
    "dev": "node --watch src/index.js",
    "start": "node dist/index.js",
    "test": "node --test",
    "build": "tsc -p .",
    "prepare": "husky"
  },
  "engines": { "node": ">=20.19" },
  "dependencies": { "fastify": "^5.0.0" },
  "devDependencies": { "typescript": "^5.6.0" },
  "peerDependencies": { "react": ">=18" },
  "overrides": { "some-nested-lib": "2.1.4" }
}
```

| Поле | Назначение |
|---|---|
| `dependencies` | нужны приложению в рантайме; ставятся всегда |
| `devDependencies` | тесты, линтеры, сборщики; **не ставятся** при `npm install --omit=dev` и в продакшен-образе |
| `peerDependencies` | библиотека требует, чтобы **у потребителя** была совместимая версия пакета (плагины, React-компоненты); избегает дублей |
| `optionalDependencies` | установка не обязательна; ошибка установки игнорируется |
| `engines` | требуемая версия Node/npm (предупреждение, с `engine-strict` — ошибка) |
| `type` | `module` или `commonjs` — формат `.js` файлов |
| `main`/`exports` | точка входа пакета; `exports` ограничивает публичный API и поддерживает условные экспорты |
| `bin` | исполняемые файлы (CLI) |
| `files` | какие файлы попадут в опубликованный пакет |
| `scripts` | команды `npm run <имя>`; `start`, `test` можно без `run` |
| `overrides` | принудительно задать версию вложенной зависимости (например, чтобы закрыть уязвимость) |
| `private: true` | запрещает случайную публикацию |

## Semver

Формат **MAJOR.MINOR.PATCH**:

- `PATCH` — обратно совместимые исправления;
- `MINOR` — новая функциональность без ломающих изменений;
- `MAJOR` — несовместимые изменения.

| Диапазон | Допускает |
|---|---|
| `1.2.3` | ровно эту версию |
| `^1.2.3` | `>=1.2.3 <2.0.0` (менять можно minor и patch) |
| `~1.2.3` | `>=1.2.3 <1.3.0` (только patch) |
| `^0.2.3` | `>=0.2.3 <0.3.0` — для `0.x` каретка осторожнее: меняться может только patch |
| `^0.0.3` | только `0.0.3` |
| `>=1.2.0 <2` | явный диапазон |
| `*` / `latest` | любая версия (опасно) |

Семвер — это соглашение, а не гарантия: даже patch-релиз может сломать вас, поэтому нужны lock-файл и тесты. Пререлизы (`1.0.0-beta.1`) диапазоны `^` по умолчанию не включают.

## Lock-файл и воспроизводимость

`package-lock.json` фиксирует **точные версии и хеши** (integrity) всех пакетов дерева, включая транзитивные. Его **коммитят в репозиторий** (для приложений).

| Команда | Поведение |
|---|---|
| `npm install` | ставит по `package.json` с учётом lock-файла; может **обновить** lock-файл |
| `npm ci` | удаляет `node_modules` и ставит **строго по lock-файлу**; падает, если он не соответствует `package.json`; быстрее и предсказуемее — для CI/CD и Docker |
| `npm update` | обновляет в пределах разрешённых диапазонов |
| `npm install pkg@latest` | выходит за диапазон |

В Dockerfile: `COPY package*.json ./` → `RUN npm ci --omit=dev` → `COPY . .`: слой с зависимостями кэшируется, пока не меняются манифесты.

## node_modules и разрешение модулей

- `require("x")` ищет `node_modules/x` в текущем каталоге, затем в родительских вверх до корня.
- npm **hoist-ит** (поднимает) зависимости в плоскую структуру, чтобы избежать дублей. Побочный эффект — **phantom dependencies**: код может импортировать пакет, которого нет в `package.json`, но он есть в `node_modules` как чья-то зависимость. Он «работает» случайно и ломается при смене менеджера или дерева.
- Если разные пакеты требуют несовместимые версии одной библиотеки, npm кладёт копии во вложенные `node_modules` (дубликаты).
- **pnpm** хранит пакеты в едином content-addressable хранилище и создаёт симлинки: экономит место и время, строгая изоляция (нет phantom dependencies). **Yarn** (Classic/Berry; Berry поддерживает Plug'n'Play без `node_modules`).

## Полезные команды

```bash
npm ls <pkg>        # кто и какую версию устанавливает
npm explain <pkg>   # почему пакет в дереве
npm outdated        # что можно обновить
npm audit           # известные уязвимости; npm audit fix — автоисправление
npm dedupe          # убрать дубликаты
npm pack            # посмотреть, что попадёт в публикуемый пакет (tarball)
npx <cli>           # запустить пакет без глобальной установки
npm run <script> --workspaces   # запуск скрипта во всех воркспейсах
```

Жизненный цикл скриптов: `pre<имя>` и `post<имя>` выполняются автоматически вокруг скрипта; при установке запускаются `preinstall`, `install`, `postinstall`, `prepare` — **скрипты зависимостей выполняют произвольный код** на вашей машине.

## Workspaces (монорепозитории)

```json
{ "private": true, "workspaces": ["packages/*"] }
```

Пакеты внутри репозитория линкуются друг к другу, зависимости ставятся единожды в корне. Для сборки и кэширования в больших монорепо добавляют Turborepo/Nx.

## Supply chain: риски и защита

Угрозы:

- **Известные уязвимости** (CVE) в зависимостях, часто транзитивных.
- **Typosquatting**: пакет с похожим именем (`lodahs`).
- **Dependency confusion**: публичный пакет с именем внутреннего, но с большей версией.
- **Вредоносные скрипты установки** (`postinstall`), «захват» аккаунта мейнтейнера, подмена пакета новой версией.
- **Заброшенные пакеты** и «левые» мейнтейнеры (инциденты с `event-stream`, `left-pad`).

Меры:

- коммитить lock-файл; `npm ci` в CI;
- `npm audit` и автоматические PR (Dependabot, Renovate) с ревью изменений;
- ограничить скрипты установки (`--ignore-scripts` либо разрешать выборочно), не запускать установку от root;
- минимизировать число зависимостей, выбирать поддерживаемые пакеты;
- scoped-пакеты и приватный реестр для внутренних пакетов (защита от dependency confusion);
- включить 2FA для публикаций, публиковать с **provenance** (подтверждение происхождения сборки);
- закреплять версии критичных пакетов, использовать `overrides` для срочных исправлений.

## Частые follow-up вопросы

**Что произойдёт, если не закоммитить lock-файл?**
Разные машины и сборки получат разные версии транзитивных зависимостей: «у меня работает, а в CI/проде нет».

**Нужно ли коммитить `node_modules`?**
Нет: восстанавливается по lock-файлу; добавьте в `.gitignore`.

**Что такое `peerDependencies` простыми словами?**
Библиотека говорит: «я работаю вместе с React версии X; поставь его сам». Так в приложении будет один экземпляр React, а не два.

**Почему `devDependencies` не нужны в продакшен-образе?**
Меньше размер образа и поверхность атаки; в Docker используют `npm ci --omit=dev` (или многостадийную сборку).

**Что делает `^` для версии `0.x`?**
Ограничивает минорную версию: `^0.2.3` допускает только `0.2.x` (>=0.2.3).

**Глобальные установки (`npm i -g`)?**
Для проектных инструментов лучше локальные devDependencies и `npx`, чтобы версии были воспроизводимы.

## Типичные ошибки

- Не коммитить lock-файл или править его вручную.
- Использовать `npm install` вместо `npm ci` в CI.
- Класть в `dependencies` инструменты сборки (и наоборот: рантайм-пакеты в `devDependencies`, из-за чего продакшен падает).
- Ставить пакеты с `latest`/`*`.
- Слепо принимать `npm audit fix --force` (он может сделать мажорные обновления).
- Импортировать пакет, которого нет в собственном `package.json`.
- Игнорировать предупреждения о deprecated/unmaintained пакетах.
