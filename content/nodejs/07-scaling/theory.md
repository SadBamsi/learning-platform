> **Ответ за 30 секунд.** Один процесс Node.js исполняет JS на одном ядре. Чтобы использовать все ядра и не блокировать event loop, есть три механизма. **`worker_threads`** — потоки внутри одного процесса с отдельным V8-изолятом и event loop; общаются через `postMessage` (копирование/transfer) или `SharedArrayBuffer`; подходят для **CPU-bound** задач. **`child_process`** (`spawn`/`fork`/`exec`) — отдельные процессы, полная изоляция, общение через IPC/stdio; подходят для запуска внешних программ и тяжёлых изолированных задач. **`cluster`** — несколько процессов-воркеров, разделяющих один порт; подходит для масштабирования HTTP-сервера на ядра одной машины. В продакшене чаще масштабируют **горизонтально**: несколько stateless-инстансов (контейнеров) за балансировщиком.

## Сравнение механизмов

| | `worker_threads` | `child_process` | `cluster` |
|---|---|---|---|
| Единица | поток (изолят V8) | процесс | процесс |
| Память | отдельная куча, можно делить `SharedArrayBuffer` | полностью изолирована | изолирована |
| Общение | `postMessage`, `SharedArrayBuffer`, `Atomics` | IPC-канал (`fork`), stdio | IPC с primary-процессом |
| Накладные расходы | ниже (быстрый старт, меньше памяти) | выше | выше |
| Падение | исключение в воркере — событие `error`, процесс жив | падает только дочерний процесс | падает только воркер |
| Типичный случай | CPU-bound: хеширование, парсинг, сжатие, картинки | запуск внешних утилит (`ffmpeg`, `git`), изоляция | HTTP-сервер на все ядра |

## worker_threads

```js
// main.mjs
import { Worker } from "node:worker_threads";

function runInWorker(n) {
  return new Promise((resolve, reject) => {
    const w = new Worker(new URL("./fib-worker.mjs", import.meta.url), { workerData: { n } });
    w.once("message", resolve);
    w.once("error", reject);
    w.once("exit", (code) => code !== 0 && reject(new Error(`worker exit ${code}`)));
  });
}
console.log(await runInWorker(40));
```

```js
// fib-worker.mjs
import { parentPort, workerData } from "node:worker_threads";
const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));
parentPort.postMessage(fib(workerData.n));
```

Важные детали:

- **Данные копируются** (алгоритм structured clone). Большие `ArrayBuffer` можно **передать** без копирования через `transferList` (в отправителе буфер станет непригодным) или **разделить** через `SharedArrayBuffer` (тогда нужны `Atomics` для синхронизации, иначе гонки данных).
- Создание воркера дорого (десятки миллисекунд, отдельная куча). Для частых задач используют **пул воркеров** (библиотека `piscina` или своя очередь), а не новый воркер на каждую задачу.
- Воркеры **не ускоряют I/O**: для него уже есть libuv. Они нужны для вычислений.
- Воркеры не делят глобальные переменные и модульный кэш: у каждого свой экземпляр модулей.

## child_process

```js
import { spawn, fork, execFile } from "node:child_process";

// spawn: стримы stdin/stdout, подходит для больших объёмов данных
const p = spawn("ffmpeg", ["-i", "in.mp4", "out.webm"]);

// fork: новый процесс Node.js с IPC-каналом (child.send / process.on("message"))
const child = fork("./task.js");

// execFile: буферизует вывод (ограничение maxBuffer), без shell
execFile("git", ["rev-parse", "HEAD"], (err, stdout) => {});
```

Безопасность: **`exec` и `spawn` с `shell: true` запускают команду через shell**. Если в строку попал пользовательский ввод — это **command injection**. Используйте `execFile`/`spawn` с массивом аргументов и без shell.

## cluster

```js
import cluster from "node:cluster";
import http from "node:http";
import os from "node:os";

if (cluster.isPrimary) {
  for (let i = 0; i < os.availableParallelism(); i++) cluster.fork();
  cluster.on("exit", (worker, code) => {
    console.log(`worker ${worker.process.pid} умер (${code}), поднимаем нового`);
    cluster.fork();
  });
} else {
  http.createServer((req, res) => res.end(`pid ${process.pid}\n`)).listen(3000);
}
```

Primary-процесс принимает соединения и распределяет их между воркерами (на Linux/macOS по умолчанию round-robin). У каждого воркера **своя память**, поэтому:

- состояние в переменных процесса (кэш, сессии, счётчики, WebSocket-подключения) **не общее**;
- для общего состояния нужен внешний стор (Redis, БД).

На практике `cluster` часто заменяют менеджером процессов (**PM2** в cluster-режиме) или запуском нескольких контейнеров/подов под оркестратором (Kubernetes), где масштабирование и перезапуск — забота платформы.

## Горизонтальное масштабирование

Чтобы запустить N копий сервиса за балансировщиком, сервис должен быть **stateless**:

- сессии и кэш — во внешнем хранилище (Redis, БД), а не в памяти процесса;
- загруженные файлы — в объектном хранилище (S3), не на локальном диске;
- фоновые задачи и cron — в очереди (BullMQ/RabbitMQ) с одним потребителем на задачу, а не «в каждом инстансе»;
- конфигурация — из переменных окружения (12-factor);
- WebSocket: либо **sticky sessions** (балансировщик привязывает клиента к одному инстансу), либо шина сообщений между инстансами (Redis pub/sub, адаптеры socket.io);
- health-checks (`/health`, readiness/liveness) и **graceful shutdown**.

**Вертикальное** масштабирование (больше CPU/RAM на одной машине) проще, но ограничено и не даёт отказоустойчивости.

## Как выбирать

| Задача | Решение |
|---|---|
| Тяжёлое вычисление в запросе (хеш, разбор, ресайз картинки) | пул `worker_threads` или вынос в очередь + отдельный воркер-сервис |
| Запуск внешней программы | `child_process.spawn`/`execFile` |
| Нужна полная изоляция/отказоустойчивость задачи | отдельный процесс |
| Нагрузить все ядра одной машины HTTP-сервером | несколько процессов (PM2/`cluster`/контейнеры) |
| Рост нагрузки сверх одной машины | горизонтальное масштабирование + балансировщик |
| Долгие и ненадёжные задачи (письма, отчёты) | очередь задач с ретраями (BullMQ, RabbitMQ, SQS) |

## Частые follow-up вопросы

**Чем воркер отличается от `cluster`-воркера?**
Воркер из `worker_threads` — поток внутри процесса (изолят V8), может делить память через `SharedArrayBuffer`. Воркер `cluster` — отдельный процесс ОС.

**Ускорит ли `worker_threads` запросы к БД?**
Нет. Запросы к БД — I/O, он не блокирует event loop. Воркеры нужны для CPU-нагрузки.

**Почему в cluster нельзя хранить сессии в памяти?**
Следующий запрос того же пользователя может попасть в другой процесс, в котором сессии нет.

**Что такое sticky sessions?**
Балансировщик направляет все запросы одного клиента на один и тот же инстанс (по cookie или IP). Нужны, когда состояние локально (WebSocket-соединения, long polling). Минус: неравномерная нагрузка, потеря сессий при падении инстанса.

**Как обновлять сервис без простоя?**
Rolling-обновление: поднимать новые инстансы, дожидаться readiness, переключать трафик, старые останавливать с graceful shutdown.

## Типичные ошибки

- Создавать новый `Worker` на каждый запрос.
- Использовать воркеры для I/O-bound задач.
- Хранить состояние в памяти процесса и масштабировать горизонтально.
- Запускать `exec` с конкатенацией пользовательского ввода.
- Не обрабатывать падение воркера/процесса и не перезапускать его.
- Ожидать, что `postMessage` передаёт объекты по ссылке: это копия.
