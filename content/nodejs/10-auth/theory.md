> **Ответ за 30 секунд.** **Аутентификация** отвечает на вопрос «кто вы?», **авторизация** — «что вам разрешено?». Два основных подхода к хранению входа: **серверные сессии** (в cookie лежит случайный идентификатор, данные — в Redis/БД; легко отозвать, но нужно общее хранилище) и **JWT** (подписанный токен с утверждениями; сервер проверяет подпись и не хранит состояние, но токен трудно отозвать до истечения срока). На практике используют **короткоживущий access-токен + долгоживущий refresh-токен** с ротацией, refresh кладут в `httpOnly`/`Secure`/`SameSite` cookie. Пароли хранят только как хеш медленным алгоритмом с солью (**argon2id**, scrypt, bcrypt). Для входа через внешних провайдеров — **OAuth 2.0 Authorization Code + PKCE** и **OpenID Connect**.

## Серверные сессии

1. Пользователь вводит логин/пароль.
2. Сервер проверяет, создаёт сессию в хранилище (Redis), отдаёт клиенту **случайный непредсказуемый идентификатор** в cookie.
3. На каждом запросе браузер присылает cookie, сервер по id находит сессию.

```js
res.setHeader("Set-Cookie",
  `sid=${sid}; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600`);
```

Флаги cookie:

- **HttpOnly** — недоступна из JS (защита от кражи через XSS);
- **Secure** — только по HTTPS;
- **SameSite=Lax|Strict** — не отправляется при большинстве кросс-сайтовых запросов (защита от CSRF);
- **Path/Domain/Max-Age** — область и срок жизни.

Плюсы: мгновенный отзыв (удалить запись), данные на сервере, маленький cookie. Минусы: нужно общее хранилище при нескольких инстансах, дополнительный запрос на каждый запрос.

## JWT

**JSON Web Token** — три части в base64url через точку: `header.payload.signature`.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiI0MiIsImV4cCI6MTc... . 5xk3...
      {"alg":"HS256","typ":"JWT"}          {"sub":"42","exp":...}        HMAC(header.payload, secret)
```

Критически важно:

- **Payload не зашифрован**, а лишь закодирован: любой может его прочитать. Не кладите туда секреты.
- Подпись гарантирует **целостность** (никто не изменил), а не конфиденциальность.
- Стандартные claims: `sub` (субъект), `iss` (издатель), `aud` (аудитория), `exp` (срок), `iat`, `nbf`, `jti` (id токена).
- **HS256** — симметричная подпись (общий секрет), **RS256/ES256** — асимметричная (подписывает приватный ключ, проверяют по публичному: удобно для микросервисов и внешних проверяющих).

### Правила проверки

```js
// Обязательно: фиксируем допустимые алгоритмы, проверяем exp, iss, aud
jwt.verify(token, publicKey, { algorithms: ["RS256"], issuer: "https://auth.example.com", audience: "api" });
```

Классические уязвимости:

- **`alg: none`** и **algorithm confusion** (подмена RS256 → HS256 с публичным ключом как секретом): всегда задавайте список разрешённых алгоритмов на сервере, не доверяйте заголовку токена.
- Слабый секрет HS256 (подбирается офлайн).
- Непроверенные `exp`, `aud`, `iss`.
- Чувствительные данные в payload.

### Сессии против JWT

| | Сессии | JWT |
|---|---|---|
| Состояние | на сервере | в токене (stateless) |
| Отзыв | мгновенный | сложный: ждать `exp`, denylist по `jti`, версия токена |
| Масштабирование | общее хранилище | проверка по подписи, без хранилища |
| Размер | маленький cookie | больше (несёт claims) |
| Кросс-сервисность | нужно общее хранилище | токен проверяется любым сервисом |
| Типичное применение | классические веб-приложения | API, микросервисы, мобильные клиенты |

«JWT лучше» — миф: для обычного веб-приложения серверные сессии проще и безопаснее. JWT оправдан, когда много сервисов проверяют токен независимо.

## Access + refresh токены

- **Access-токен**: короткий срок (5–15 минут), отправляется с каждым запросом (`Authorization: Bearer …`).
- **Refresh-токен**: долгий срок (дни), используется только для получения новой пары токенов; хранится на сервере (хеш) для возможности отзыва.
- **Ротация**: при каждом обновлении выдаётся **новый** refresh, старый становится недействительным. Если предъявлен **уже использованный** refresh — это признак кражи: отзываем всю «семью» токенов и просим войти заново (**reuse detection**).

## Где хранить токены в браузере

| Место | Риск |
|---|---|
| `localStorage` / `sessionStorage` | читается любым скриптом: **XSS ⇒ кража токена** |
| Память (переменная JS) | теряется при перезагрузке, но не крадётся «оптом» |
| **`httpOnly` cookie** | JS не прочитает (XSS не украдёт токен), но браузер отправит её автоматически ⇒ нужна защита от **CSRF** (`SameSite`, CSRF-токен) |

Частый рекомендуемый вариант: access-токен в памяти, refresh-токен в `httpOnly; Secure; SameSite` cookie с узким `Path` (`/auth/refresh`).

## Хранение паролей

- Никогда не храните пароль в открытом виде или обратимо зашифрованным.
- **Обычные хеши (MD5, SHA-1, SHA-256) не подходят**: они быстрые, и пароли подбираются миллиардами попыток в секунду.
- Используйте **медленные адаптивные** алгоритмы: **argon2id** (рекомендуемый выбор), **scrypt**, **bcrypt** (учтите ограничение на длину пароля 72 байта). Параметры стоимости подбирают под ваше железо.
- **Соль** — уникальная случайная для каждого пароля (защита от rainbow tables и одинаковых хешей). Обычно хранится вместе с хешем.
- Сравнение хешей — только **за постоянное время** (`crypto.timingSafeEqual`), иначе возможна атака по времени.
- Параметры алгоритма храните в самой строке хеша, чтобы можно было их усиливать и перехешировать при следующем входе.

```js
import { scrypt, randomBytes, timingSafeEqual } from "node:crypto";
import { promisify } from "node:util";
const scryptAsync = promisify(scrypt);

export async function hashPassword(password) {
  const salt = randomBytes(16);
  const key = await scryptAsync(password, salt, 64);
  return `scrypt$${salt.toString("base64")}$${key.toString("base64")}`;
}

export async function verifyPassword(password, stored) {
  const [, saltB64, keyB64] = stored.split("$");
  const key = Buffer.from(keyB64, "base64");
  const candidate = await scryptAsync(password, Buffer.from(saltB64, "base64"), key.length);
  return timingSafeEqual(candidate, key);
}
```

(В продакшене используйте проверенные библиотеки `argon2`/`bcrypt` и настройку параметров стоимости.)

## OAuth 2.0 и OpenID Connect

- **OAuth 2.0** — протокол **делегирования авторизации**: приложение получает **ограниченный доступ** к ресурсам пользователя у провайдера (Google, GitHub), не зная пароля.
- **OpenID Connect (OIDC)** — надстройка над OAuth 2.0 для **аутентификации**: добавляет `id_token` (JWT с данными о пользователе).

**Authorization Code Flow + PKCE** (стандарт для веб и мобильных приложений):

1. Клиент генерирует `code_verifier` (случайная строка) и `code_challenge = SHA256(verifier)`.
2. Перенаправляет пользователя к провайдеру с `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge`.
3. Пользователь входит и даёт согласие; провайдер возвращает на `redirect_uri` одноразовый `code` и `state`.
4. Клиент (бэкенд) проверяет `state` (защита от CSRF) и обменивает `code` + `code_verifier` на токены.
5. PKCE гарантирует, что код может использовать только тот, кто его запросил (защита от перехвата кода).

Роли: *resource owner* (пользователь), *client* (ваше приложение), *authorization server* и *resource server*.

## Авторизация

- **RBAC** (роли: admin, editor) — просто и широко; **ABAC** (атрибуты и политики) — гибко.
- Проверка прав — **на сервере и на каждом запросе**, не на клиенте.
- Не доверяйте `userId`, пришедшему от клиента: берите из проверенного токена/сессии.
- **IDOR/BOLA** — доступ к чужому объекту подстановкой id (`/orders/123`): всегда проверяйте владение ресурсом.
- Принцип наименьших привилегий и deny by default.

## Защита входа

- Rate limiting и экспоненциальные задержки для `/login`, `/reset-password`.
- Одинаковое сообщение «неверный логин или пароль» (не выдавать, существует ли email).
- Многофакторная аутентификация (TOTP, WebAuthn/passkeys).
- Одноразовые токены сброса пароля с коротким сроком, хранение их хеша.
- Инвалидация сессий/refresh-токенов при смене пароля.

## Частые follow-up вопросы

**Можно ли «разлогинить» пользователя с JWT?**
Только косвенно: короткий `exp` + хранение refresh-токенов на сервере (отзыв refresh), denylist `jti`, поле «версия токена» в БД. Чистый stateless-JWT до истечения срока валиден.

**HS256 или RS256?**
HS256 — один секрет у всех проверяющих (подойдёт, если токен выпускает и проверяет один сервис). RS256/ES256 — проверяющим достаточно публичного ключа (JWKS), приватный ключ остаётся у издателя.

**Что такое CSRF и почему он касается cookie-аутентификации?**
Браузер автоматически прикладывает cookie к запросам на ваш домен, даже если запрос инициирован чужой страницей. Защита: `SameSite`, CSRF-токены, проверка `Origin`.

**Почему bcrypt/argon2, а не SHA-256 с солью?**
SHA-256 слишком быстрый: на GPU перебираются миллиарды вариантов в секунду. Адаптивные алгоритмы намеренно дороги по CPU/памяти.

**Зачем `state` в OAuth?**
Привязывает ответ провайдера к исходной сессии пользователя и защищает от подделки запроса (CSRF).

## Типичные ошибки

- Хранить JWT в `localStorage` без осознания XSS-риска.
- `jwt.verify(token, secret)` без списка алгоритмов, без проверки `aud`/`iss`.
- Долгоживущий access-токен без возможности отзыва.
- Сравнивать хеши/токены через `===`.
- Класть в JWT пароли, персональные данные, права «навсегда».
- Авторизация только на фронтенде.
- Отсутствие rate limit на логине и сбросе пароля.
